DETAILS:

  [app/core/config.py]

        - A 6h window deviating more than this percentage from the daily mean
          is flagged as an anomaly.
      PREDICTION_MAX_DAYS: int = 7
        - Maximum number of future days allowed for prediction mode.

  [app/agents/state.py]

      time_mode: str   # "single_day" or "date_range"

    In WaterSystemState, add:
      mode: str

  [app/models/river.py]
    Add new Pydantic models (keep all existing models unchanged):

      class CausalFactor(BaseModel):
        factor: str
          # Source of influence, e.g. "Upstream COMID 12345" or "ICIS facility XYZ"
        direction: str
          # "increasing" / "decreasing" / "neutral"
        magnitude: str
          # "high" / "medium" / "low"
        evidence: str
          # Specific evidence supporting the judgment

      class HydrologyExplanation(BaseModel):
        primary_drivers: List[CausalFactor]
          # All identified causal factors
        reasoning_chain: str
          # Full step-by-step causal reasoning,
          # e.g. "A causes B, B affects C through mechanism D"
          # In prediction mode, must also explain why values change over time.
        uncertainty_sources: str
          # Description of what makes this inference uncertain

      class AnomalyWindow(BaseModel):
        time_window: str
          # e.g. "2026-01-03 06:00 to 12:00"
        parameter: str
        observed_value: float
        daily_mean: float
        deviation_pct: float
          # Percentage deviation from daily mean
        possible_cause: str
          # LLM-inferred explanation for the anomaly

      class DailyParameterResult(BaseModel):
        date: str
        representative_value: Optional[float]
          # Daily mean, used as the single output value for that day
        unit: Optional[str]
        confidence: float
        anomalies: List[AnomalyWindow] = []
          # Anomalous 6h windows detected within this day (if any)

      class ParameterResult(BaseModel):
        name: str
        code: str
        unit: Optional[str]
        daily_results: List[DailyParameterResult]
          # Single-day mode: exactly one entry
          # Date-range mode: one entry per day

    Extend existing HydrologyInference (keep all existing fields):
      Add:
        detailed_results: List[ParameterResult] = []
          # Full daily breakdown for frontend display
        explanation: Optional[HydrologyExplanation] = None
          # Always present in final output

    Note:
      The existing "parameters" field is kept for upstream data passing
      between LLM agents (upstream_results). The new "detailed_results"
      field is for frontend display only.

SPRINT 2 - NWIS Daily Summary and Anomaly Detection
================================================================================

GOAL:
  Add a utility method in NWISService that takes the existing 6h sampled data
  and computes: (1) daily representative values, (2) anomaly windows.
  This is pure data processing with no LLM involvement, so it can be
  tested independently with real USGS data.

FILES TO MODIFY:
  - app/services/nwis_service.py

DETAILS:

  [app/services/nwis_service.py]
    Add static method: compute_daily_summary(raw_data, anomaly_threshold_pct)

    Input:
      raw_data: the dict returned by get_daily_averages()
        (contains "averages" list with 6h data per parameter)
      anomaly_threshold_pct: from settings.ANOMALY_THRESHOLD_PCT

    Processing per parameter:
      1. Group 6h data points by calendar date.
      2. Compute daily mean as the representative value for that day.
      3. For each 6h window, compute deviation from daily mean:
           deviation_pct = abs(value - daily_mean) / daily_mean * 100
         If deviation_pct >= anomaly_threshold_pct, create an AnomalyWindow.
      4. Build a DailyParameterResult for each day.
      5. Build a ParameterResult wrapping all daily results.

    Output:
      List[ParameterResult]

    Logging:
      Log the number of days processed and total anomalies found per parameter.
      Example:
        "[NWISService] Site 12345 | pH | 7 days processed | 2 anomalies detected"

TESTABLE CHECKPOINT:
  - Write a small standalone test script (test_sprint2.py in project root):

SPRINT 3 - Weather Forecast API
================================================================================

GOAL:
  Add get_weather_forecast() to WeatherService using the NOAA forecast API.
  This enables the Prediction mode to have real future weather data
  instead of relying solely on the LLM's internal knowledge.

FILES TO MODIFY:
  - app/services/weather_service.py

DETAILS:

  [app/services/weather_service.py]
    Add static method: get_weather_forecast(lat, lon, start_date, end_date)

    NOAA API flow:
      Step 1: GET https://api.weather.gov/points/{lat},{lon}
        -> Extract "forecastHourly" URL from response properties
      Step 2: GET {forecastHourly URL}
        -> Returns hourly forecast for approximately the next 7 days

    Processing:
      1. Filter forecast periods to the requested date range.
      2. Aggregate to daily values (resample using same WEATHER_FREQ setting
         as existing observations, to keep format consistent).
         - temperature: daily mean
         - precipitation probability: daily mean (as proxy for precipitation)
      3. Build output in the same format as existing get_weather_and_alerts()
         "observations" list:
           [{"time": ISO string, "temp_c": float, "precip_mm": float}, ...]

    Caching:
      Use existing weather_cache with expire=3600
      (NOAA forecast updates approximately hourly)

    Cache key format:
      "forecast_{lat}_{lon}_{start_date}_{end_date}"

    Logging:
      "[WeatherService] Forecast fetched for ({lat}, {lon}):
       {n} daily entries from {start} to {end}"

    Error handling:
      If NOAA returns non-200 or empty, return {"observations": [], "alerts": []}
      and log a warning. Do not raise exceptions (matches existing behavior).

SPRINT 4 - Time Mode Detection and Split-Range Handling
================================================================================

GOAL:
  Update AskerService to automatically detect mode and time_mode from the
  user-specified date range. Handle the mixed-range case (part historical,
  part future) by splitting into two time segments.

FILES TO MODIFY:
  - app/services/asker_service.py
  - app/core/config.py (already modified in Sprint 1)

DETAILS:

  [app/services/asker_service.py]
    In prepare_inference_context(), after parsing start_date and end_date:

    Step 1 - Determine time_mode:
      if start_date == end_date:
          time_mode = "single_day"
      else:
          time_mode = "date_range"

    Step 2 - Determine mode and handle mixed ranges:
      today = date.today()
      start = date.fromisoformat(start_date)
      end = date.fromisoformat(end_date)

      Case A - Fully historical (end <= today):
          mode = "gap_filling"
          segments = [{"start": start_date, "end": end_date,
                       "mode": "gap_filling"}]

      Case B - Fully future (start > today):
          mode = "prediction"
          # Enforce 7-day cap
          if (end - start).days > settings.PREDICTION_MAX_DAYS:
              end = start + timedelta(days=settings.PREDICTION_MAX_DAYS)
              end_date = end.isoformat()
              log warning that range was capped
          segments = [{"start": start_date, "end": end_date,
                       "mode": "prediction"}]

      Case C - Mixed (start <= today < end):
          mode = "mixed"
          hist_end = today.isoformat()
          pred_start = (today + timedelta(days=1)).isoformat()
          # Enforce 7-day cap on prediction segment
          pred_end = end_date
          if (end - today).days > settings.PREDICTION_MAX_DAYS:
              pred_end = (today + timedelta(
                           days=settings.PREDICTION_MAX_DAYS)).isoformat()
              log warning
          segments = [
              {"start": start_date, "end": hist_end,  "mode": "gap_filling"},
              {"start": pred_start, "end": pred_end,  "mode": "prediction"}
          ]

    Add "mode", "time_mode", and "segments" to the returned context dict.

    Logging:
      "[AskerService] time_mode={time_mode} | mode={mode}"
      "[AskerService] Segments: {segments}"
      For mixed: "[AskerService] Mixed range detected. Splitting into
                  historical ({start} to {hist_end}) and
                  prediction ({pred_start} to {pred_end})"
