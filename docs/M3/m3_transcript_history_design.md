## 2. 已确认决策

### D01：运行中持久化失败仍继续分析

分析已经启动后，transcript 写入失败不直接终止分析。保留未落盘内容，允许后续补写。

分析成功后，按 D38 固定终态选定前已产生的必需结果、过程和状态的写入范围；该范围在 D04 交付窗口到期时仍未保存完整，则交付当前结果，进入 `completed_with_persistence_error`，发布带安全 warning/error_id 的唯一 `session_completed`。终态自身及后续收尾记录保存失败时保留已选定终态，由当前读取接口返回持久化警告。任何必需写入尚未确认时均禁止清理 live state。用户接受进程在补写前退出或崩溃时，未落盘内容可能丢失。

适用：`M3-C08`、`M3-C11`、`M3-C12`。

### D02：创建先持久化，成功后启动 workflow

创建事务保存 session 创建信息、完整业务请求 item 和携带 configuration snapshot 的原 `session_created` item；适用的幂等 key、原请求体指纹及一份小型不可变创建回执保存在同一 session 行，具体职责按 D33。事务成功后才启动分析；已确认创建提交时返回 `201` 和原创建回执，提交后启动失败按 D16 记录。确认创建写入失败时返回安全的 `503`，不启动分析。

创建提交结果不确定、HTTP 断开的具体收敛流程仍需细化；不能把“客户端未收到成功”直接等同于“数据库未提交”。提交后 task 明确启动失败的对外行为按 D16 执行。

适用：`M3-C03`、`M3-C08`、`M3-C09`。

### D03：运行中异步增量落库

过程内容产生后进入 `LiveTranscriptBuffer`，通过统一记录入口按 D56 的 run 内追加顺序异步保存数据库。分析结束时按 D38 核对终态选定前固定范围内的必需写入；清理资格仍按 D19 核对包括终态和适用收尾记录在内的全部必需写入。

入队、创建 task 和写入 live buffer 不代表持久化成功；成功确认必须来自实际 durable commit。历史数据在写入进行期间可能暂时落后于实时进度。

写入触发、组批和失败批次的顺序按 D37；空闲写入器收到待保存内容就开始，不额外等待合批。

适用：`M3-C01`、`M3-C08`、`M3-C12`。

### D04：失败补写、有限重试与交付时机

- 首次写入不计为重试。同一轮连续失败最多重试 5 次。
- 第 1–5 次重试分别在前次尝试失败或超时后等待 `1 / 2 / 4 / 8 / 16` 秒。计时从前次尝试结束开始。
- 运行期间与分析结束后共用这一轮连续失败的计数；分析结束不重新计数。写入恢复成功才重置退避与连续失败计数。
- 同一 session 串行写入；新 item 到来不额外启动重试，也不重置预算或计时。
- 分析结束且 D38 固定范围内的必需写入仍未保存完整时，等待第 3 次重试失败后的 2 秒窗口到期，再交付 `completed_with_persistence_error`。如果该窗口在分析结束前已到期，则不重新等待。如果期间该范围已全部确认保存成功，则正常完成。终态自身或后续收尾写入失败按 D38 表达警告，不再重新选择终态。
- 原先建议的“完成时最多等待 5 秒”已被替换，不再使用。
- 第 4、5 次可用于终态交付后的后台补写。第 5 次仍失败时停止自动重试，保留未落盘内容与 live state。
- 耗尽后由用户按 D39 主动触发“重试保存”，才可开启新一轮；数据库恢复、页面刷新或新内容到来不自动重置耗尽预算。
- 补写复用原 item/event 身份，不重复追加事实，不重新执行分析。
- 补写成功不将 `completed_with_persistence_error` 改写为 `completed`，不再发布第二个终态事件。保留当时的 warning/error_id，并记录恢复事实。
- 补写完整且满足 `persistence_confirmed + workflow_quiesced + grace period elapsed` 后，可以清理 live state。“持久化失败不得清理”解释为失败尚未修复时不得清理。
- 显式 cancel 继续立即提交并返回；不等待上述完成交付窗口。

单次数据库写入预算按 D36，成功仅确认该批覆盖的写入，原失败批次与后续内容的顺序按 D37，终态选定与 cancel 的边界按 D38，耗尽后的手动恢复按 D39。具体路由、读取状态/错误 DTO 和提交核实操作仍需细化。不得在 adapter 内叠加隐藏重试来突破上述预算。

适用：`M2-C03`–`M2-C06`、`M3-C10`–`M3-C13`。

### D05：第一版直接使用 PostgreSQL

PostgreSQL 统一保存 run、独立 Agent session、创建幂等信息、append-only transcript 和完整大内容。元信息、timeline item 和大内容分别组织，timeline 通过 preview/reference 支持按需展开。四张核心表的职责按 D53，具体列与约束继续细化。

原 SQLite 提议已被 PostgreSQL 替换。用户所说的“迁移 schema”专指 SQLite → PostgreSQL 的转换；第一版直接使用 PostgreSQL 后，不存在该转换任务，也不增加历史数据搬迁任务。

新 PostgreSQL 环境的建表，以及后续功能迭代引起的表结构变更，是独立的工程事项。前轮建议采用 SQLAlchemy Core + psycopg 3，并以 Alembic 管理结构版本；初始化和升级通过 D07 的独立命令执行。

适用：`M3-C01`–`M3-C09`、`MR-G11`、`MR-G13`。

### D06：可复用的环境配置与搭建说明

用户确认本地开发默认通过 Docker Compose 启动 PostgreSQL，同时支持配置连接已有 PostgreSQL 实例，并要求其他环境也容易搭建。

M3 实现交付需要包含：

- PostgreSQL Compose 配置，数据库数据使用持久化 volume。
- 可提交的配置示例，说明数据库连接、端口、账号、数据库名与其他必要变量；真实凭据不进入版本库或普通日志。
- 环境变量的命名、加载位置与优先级，以及密码特殊字符、远端连接要求的配置方式。
- macOS、Windows、Linux 的搭建说明，覆盖本地 Compose 和已有 PostgreSQL 两种方式。
- 初始化、后续启动、正常停止、保留数据库数据以及检查服务可用性的步骤。
- 可复用的测试数据库配置与真实 PostgreSQL 集成验收；保持现有 Python/uv 安装入口。

具体 PostgreSQL 版本、配置字段、文件路径和命令名称尚未定型。应用继续保持单 worker；引入 PostgreSQL 不自动意味着支持多 worker。

适用：`GLOBAL-C07`、`M2-C10`、`MR-G04`、`MR-G07`、`MR-G09`、`MR-G11`。

### D07：独立命令初始化，应用启动检查

提供独立、跨平台的数据库结构初始化/升级命令。新环境搭建顺序为：填写配置 → 启动或连接 PostgreSQL → 执行初始化命令 → 启动后端。

应用启动检查数据库连接和结构版本；需要初始化或升级时给出安全、明确的提示及相应命令。应用启动本身不自动改表。启动顺序与失败退出规则按 D62，版本接受规则按 D63；命令名称、检查实现和具体失败诊断在实现设计中补齐。

适用：`M3-C01`、`MR-G04`、`MR-G07`、`MR-G09`、`MR-G11`。

### D08：Transcript 与 SSE 分别编号并保持原事件

`item_id` 是 transcript item 的固定身份，补写和重试不变，具体 UUID 身份及全文引用按 D31。按 D56，`transcript_sequence` 是 run 内完整 transcript 的统一追加顺序，run 自身记录、各 Agent session 记录及内部记录共同编号；独立 session 不再单独分配 transcript 编号，SSE 过程编号按 D78 独立处理。

当前 M2 的公开 LifecycleEvent.sequence 只对其生命周期事件编号；M3 按 D69/D78 改为实际 Agent session 的过程事件独立编号，run 通知不分配 SSE id。已有生命周期 transcript item 直接复用原事件，保留原 schema version、sequence 和发生时间，不重新构造同义事实；新两层事件的 payload 继续按实际类型定型。

完整 timeline 按 `transcript_sequence` 展示，不按写入完成时间或重试时间重新排序。记录内部事实不改变 SSE 游标。`workflow_quiesced` 等内部记录可以出现在 terminal lifecycle item 之后，不延长已终止的 SSE stream。

适用：`GLOBAL-C09`、`M2-C02`、`M2-C07`、`M2-C08`、`M3-C01`、`M3-C08`、`M3-C10`、`M3-C15`。

### D09：历史局部不可读时显式呈现

- 遇到当前代码不认识的 content type/version，保留 item ID、序号、时间、类型与版本，并明确标明当前版本无法解析。保留原内容，可通过引用读取；不将其当作已解析业务结果。
- 已知版本的内容校验失败，明确标为数据损坏并提供安全 `error_id`，不能退化成未知类型来掩盖错误。
- 其余正常 timeline item 继续返回，问题记录不静默跳过，也不改写原持久化内容。
- 新写入内容仍必须通过已知类型和版本的校验；历史容错读取不成为写入任意 payload 的入口。
- 数据库整体读取失败返回错误，不伪造空历史。

具体读取 DTO、原始内容引用与安全读取规则仍需细化。

适用：`M3-C02`、`M3-C04`、`M3-C06`、`M3-C08`、`M3-A02`、`MR-G05`、`MR-G09`。

### D10：历史分层按需加载，数据库作为读取来源

历史查询采用四层加载方式。这里描述后端查询职责与接口数据装载，不代表前端必须采用四层页面，产品交互按 D21 执行：

| 用途 | 内容 |
|---|---|
| Session 列表 | 分页返回身份、状态、时间、query 和 configuration。 |
| Session 详情 | session 信息、存在时的已持久化结果，以及 timeline 查询入口。 |
| Transcript timeline | 按 D45，一次返回所选 scope 的完整有序记录列表，包括 item 元信息、小内容或大内容 preview。 |
| 单条完整内容 | 按 reference 读取完整内容。 |

这些历史接口只读取 PostgreSQL，未落盘内容不混入历史响应。query 历史列表分页采用 cursor；timeline 按 `transcript_sequence` 升序一次返回完整记录列表，不增加 Agent 记录分页参数。打开列表或结果详情不自动下载完整 prompt、工具结果和原始输出。接口中的 inline/preview/reference 决定数据装载，前端折叠由内容语义决定，即使已内联的小型 skill/tool/hook 内容也默认折叠。

按 D44/D45，产品中的分页展示只针对 query 历史列表，水体会话记录连续展示；D45 替换原 timeline cursor 装载约定，不沿用列表/timeline 共用页大小方案。query 历史列表按 D47 默认 50 条、最多 200 条，以创建时间和 session_id 倒序进行游标分页；游标按 D48 编码，首版参数按 D49 仅保留 limit/cursor，完整 DTO 继续定型。

列表既有 configuration 响应仍保留，通过已保存的创建事件读取；这不要求 analysis_sessions 另存完整配置。列表 query 是从同一业务请求生成的少量查询投影。API 的字段不直接等同于 session 表列，按 D33 组装。

M3 尚未产生的业务结果不生成占位摘要。详情、timeline 与全文的统一路径及默认自动读取按 D42，显式历史读取按 D43 的 view=history，query 历史列表分页与参数范围按 D47–D49；水体过程按 D64 使用 run_id + session_id 定位，具体 URL 按 D65，完整 DTO 继续细化。单条完整内容在历史读取语义下仍遵守相同的持久化来源约束。D24 的当前读取职责支持尚未落盘的内容，不改变本节历史查询只读已持久化事实的定义。

适用：`M3-C01`、`M3-C04`、`M3-C05`、`M3-C07`、`M3-C08`。

### D11：可选幂等键，前端按一次主动提交管理

创建接口 `POST /api/analysis/runs` 接受可选的 `Idempotency-Key` 请求头。**前端每次主动分析生成新 key；只有同一次提交的重试才原样复用 key 和请求体。** 用户再次提交相同 query，甚至整个请求体完全相同，也必须使用新 key。前端不得按 query 缓存或复用 key。

| 请求情形 | 已确认行为 |
|---|---|
| 同 key、完全相同的请求体 | 返回原 session，不再次执行；分析已结束或服务重启不改变这一约定。 |
| 同 key、不同请求体 | 返回 `409 Conflict`，不创建新 session。 |
| 新 key、相同 query | 创建新 session，允许用户主动重新分析。 |
| 不传 key | 每次请求都创建新 session，重试可能重复创建。 |

幂等表达的是“同一次提交”，不按 query 自动合并分析。幂等映射按 D02 与创建数据一起持久化，不依赖进程内缓存。

用户要求将前端可见约定放到 M3 目录的父目录 `docs`；已在 [前端接入约定](../frontend_integration_contracts.md) 写明 key 管理、网络重试和冲突处理，并区分已确认设计与当前实现。后续接口决策需要同步该文档。

请求体匹配按 D12 执行，成功回执按 D13 返回，保留策略按 D14 执行，并发创建按 D15 执行。键格式与唯一范围按 D34。

适用：`M3-C09`、`MR-G09`。

### D12：完全相同的请求体，不额外规范化

前端只需要记住一句话：**重试时原样复用 key 和请求体。**

幂等比较使用服务端收到的原始请求体字节，不基于 Pydantic 校验后的模型或补全默认值后的 configuration 重新构造请求。不为幂等比较执行 query trim、字段排序、JSON 重新序列化或默认值合并；请求体有任何变化即按不同请求处理，包括 JSON 排版或字段顺序变化。前端可以保存首次发送的请求体，供同一次提交重发。

请求体指纹在业务规范化与默认配置解析之前计算，并与幂等映射持久化。原始 body 不因计算指纹而绕过既有脱敏边界另行落库或写入日志。实际创建时的请求校验、query trim 和配置快照仍按业务契约执行；指纹不是另一套业务请求模型。

相同 key 和原样请求体命中原 session 后使用原创建配置快照，服务端后续默认配置变化不影响匹配，也不重算原 session 配置。未命中时才进入新的创建流程。

此决策替换“按字段规则规范化后比较”的提议，并同步修订 `M3-C09` 与 `M3-A04`；它们仍是待实现、待验收的契约。

适用：`M3-C03`、`M3-C09`、`M3-A04`、`GLOBAL-C07`、`GLOBAL-C09`。

### D13：首次创建与幂等重试统一返回原创建回执

首次成功创建和命中已提交创建的幂等重试，都返回 `201 Created` 与首次创建时捕获的 session 回执。成功响应 body 保持原 `session_id`、`created_at`、创建时的 `updated_at`、configuration 和 `pending` 状态；不读取当前可变 session 状态来替换回执字段。

回执表示创建已被接受，不表示 session 目前仍在等待执行。即使分析已经完成、失败、取消或服务重启，幂等重试也不重置状态、不再次启动分析、不追加第二个 `session_created`。按 D33，提供 key 时在 analysis_sessions 保存一份原响应 body 的小型不可变快照，与 key/指纹一起提交；重试直接使用该回执，不按当前响应模型重新计算创建事实。除此之外不再复制同义创建快照；具体回执列编码和版本读取在 schema/API 设计中补齐。

前端使用返回的 `session_id` 获取后续进度，不用重试收到的 `pending` 覆盖已经获知的 running/terminal 状态。实时状态、持久化历史与重启后读取的具体边界按后续设计闭合。

回执稳定指业务 body 和成功状态码；`X-Request-ID` 仍为每次 HTTP 尝试独立生成，沿用 M2 排障约定，不重放第一次 HTTP 请求的 request ID。

已同步父目录 [前端接入约定](../frontend_integration_contracts.md)。并发创建按 D15 执行，提交后 workflow 启动失败按 D16 执行；提交结果不确定的确认流程仍待对齐。

适用：`M3-C03`、`M3-C08`、`M3-C09`、`M3-A04`、`GLOBAL-C09`、`MR-G09`。

### D14：幂等记录随 session 历史保留，不自动过期

M3 不为创建幂等记录设置自动过期时间。只要 session 历史仍在，对应 key、请求体指纹与创建回执就继续保留；分析结束、服务重启、数据库连接重建以及 live-state 清理都不删除或重置它们。

保留期内，同一次提交即使隔天重试，也按 D12/D13 返回原创建回执。M3 接受数据库持续保留每次带 key 提交的幂等记录，不增加定时过期任务。

长期保留不改变前端的新提交规则：只有重试同一次提交才复用 key；用户重新分析时始终生成新 key，与 query 或整个请求体是否相同无关。此规则已同步前端文档和前端验收清单。

M3 不提供删除历史入口。M9 实现 admin history cleanup 时必须明确历史删除后的幂等记录处置与旧 key 响应；届时不能把 live-state 内存清理当作历史删除。该后续边界归属 `M9-C06`，本决策不预先选择级联删除或保留墓碑。

适用：`M3-C09`、`M3-A04`、`M3-C12`、`M9-C06`、`GLOBAL-C10`。

### D15：同 key 的并发创建等待事务结果

同 key、完全相同请求体的请求并发到达时，只有一个请求负责创建，其他请求有界等待该创建事务的结果。等待范围限于创建事务，不等待分析执行完成。

| 创建事务结果 | 后续行为 |
|---|---|
| 确认提交成功 | 等待者读取已提交的原创建回执，按 D13 返回 `201`；不再创建 session 或再次启动 workflow。 |
| 确认回滚且未创建 session | 允许一个等待者接手创建，其余继续遵守相同的并发约束。 |
| 等待超时 | 按 D35 默认最多等 5 秒，可配置；返回 `503 / idempotency_wait_timeout / retryable=true`，客户端原样复用 key 和请求体重试。 |

以数据库唯一约束和事务确认保证不会留下重复创建；进程内协调不能替代持久化约束。同 key、不同 body 仍按 D11/D12 返回 `409`。等待超时不等于创建回滚，不释放已提交的 key、不自动取消已有 session，也不能据此启动第二次分析。

事务的提交结果暂时不确定时，不能擅自按“确认回滚”交接创建。等待上限和错误码按 D35；具体提交确认流程及创建提交后 workflow 启动的所有权在后续事务设计中补齐。

D15 的等待是创建请求协调，不使用 D04 的 transcript 后台补写预算。已经运行的分析、其他 key 的请求和其他 session 不应被同 key 等待阻塞；持久化 I/O 不能进入现有 per-session 状态/event 临界区。

已同步父目录前端接入文档。适用：`M3-C09`、`M3-A04`、`M2-C04`、`MR-G09`。

### D16：创建提交后启动失败，保留 session 并报告失败终态

创建事务已确认提交，但后台 workflow 明确未能启动时，保留 session、幂等映射和原创建回执。session 进入 `failed`，通过唯一 `session_failed` 记录 `workflow_start_failed` 和安全的 `error_id`。该事件、错误和 session 状态需要按统一持久化流程保存；尚未确认保存成功时，不宣称历史已经更新，也不清理 live state。

创建请求仍返回 `201` 与原创建回执。前端使用事件或后续状态读取获知启动失败；同 key 和原请求体重试仅返回原回执，不重新启动 workflow。用户主动再次分析必须使用新 key，创建新 session。

启动失败走 session 的统一终态与收尾流程，遵守唯一终态约束；若显式 cancel 已先提交，则维持 cancelled，不再追加失败终态。没有成功创建 workflow task 时，也必须确认不会再有后台工作后记录 quiesced，不能依赖一个不存在的 task 的 finally 回调。task 已被接受后的普通执行错误继续走 workflow 失败路径，不能因后续辅助操作失败又启动另一条收尾路径。

若进程直接崩溃，无法当场完成失败处理，则下次启动按 `M3-C14`/D61 将持久化遗留 pending/running 的 run 与 Agent session 分别标记为 `failed / service_interrupted`；已终态 run 下的遗留非终态 session 也需检查。各层已持久化的终态不重写，第一版不恢复执行。

本决策补齐 D02/D13 的提交后启动失败分支；提交结果不确定、HTTP 中断与创建任务所有权的具体协议仍需细化。已同步父目录前端接入文档。

适用：`M3-C08`、`M3-C09`、`M3-C12`、`M3-C14`、`M2-C03`–`M2-C06`、`GLOBAL-C07`、`GLOBAL-C09`。

### D17：live SSE 保持进程内续传，重启或清理后转历史

后续按 D69 采用两层流，D70 已确认正常关闭条件：session 结束并发完可见过程后关闭，run 则等待业务终态、执行收敛与必需写入全部确认。原单流的业务终态即关闭假设被替代；D77 已确认合法请求且 live state 保留时统一 200 SSE，通过 stream_end 结束，不保留旧 204 分支；重启或清理后转历史、不重跑分析和明确区分数据库错误的边界保留。

D65 的两条 SSE 路径按对应 run/session 实时状态是否仍存在决定读取方式：

| 场景 | 响应与前端行为 |
|---|---|
| 当前进程仍保留对应 live state | 按 D73，run 重连同步最新完整轻量快照、不补播旧通知，session 按游标补齐可见过程；按 D70 判断各流正常结束；结束通知按 D76 采用 stream_end，合法请求成功握手按 D77 统一 200 SSE；消费身份按 D78，具体 payload 继续定型。 |
| 服务重启或满足门槛后已清理对应 live state；数据库中仍有对应 run/session 历史 | SSE 握手返回 `410 Gone`，提供历史查询入口；前端停止对应流的 SSE 重连，转到历史详情查看状态与已保存内容。 |
| 内存和数据库均确认不存在对应 run/session | 返回 `404`。 |

`410` 仅表示原实时流已不可用，不代表分析失败，也不删除历史。历史读取遵守 D10，从 PostgreSQL 返回已保存事实；不将历史 transcript 再包装为可继续执行的实时 stream。页面刷新、网络重连和读取历史都不创建新分析、不取消原分析。

数据库读取失败时返回可排查的服务错误，不推断 session 不存在或伪造 `404`/空历史。`410` 属于 HTTP 握手响应；SSE headers 已发出后的传输故障保持流中断语义，不能在流尾追加 HTTP error JSON。

本决策不改变清理门槛：未持久化完整或 workflow 未 quiesced 时不得清理 live state。新创建事务与 runtime 注册之间的短暂窗口不能误判为历史 session；其协调方式随创建所有权协议细化。`410` 的错误码/history reference DTO 仍需补齐；前端识别握手响应的方式按 D18 执行。清理前仍未发送完的极少数慢连接按 D20 简化，不另设专门机制。

适用：`M3-C01`、`M3-C04`、`M3-C12`、`M3-C14`、`M3-C15`、`M3-A08`、`M2-C01`–`M2-C03`、`MR-G09`。

### D18：前端统一使用基于 fetch 的 SSE 客户端，由 M9 实现

后续按 D69 由同一客户端实现承接两种流。恢复语义按 D73：run 重连同步最新快照，session 按游标补齐过程；下述消费游标只用于 session 过程流，不要求 run 补播旧通知。正常结束按 D70，不能从 run 业务终态推断 run 通知流已结束；消费身份按 D78、成功握手按 D77，具体事件格式和错误正文继续定型。

前端统一封装基于 fetch 的 SSE 客户端，读取 HTTP 响应后决定是消费事件流还是处理错误，不能假设原生 EventSource 的 error 回调可以提供 HTTP 状态码和错误正文。

该客户端承担以下职责：

- `200` 且响应为 `text/event-stream` 时流式解析事件，遵守对应公开事件 schema；不能把任意网络分块直接当作完整事件。
- 按 session 保存最后确认消费的公开 sequence，断线重连时通过 `Last-Event-ID` 续传，并按事件身份去重。
- 按 D77，合法请求且 live state 保留时用 `200` SSE 和 `stream_end` 处理正常结束，不再使用旧 `204` 分支；`410` 停止重连并按返回的入口读取历史；`404` 展示记录不存在；其他 HTTP 错误按统一错误契约处理。重连次数和退避策略另行定型，不套用数据库补写的 5 次预算。
- 按 D70 分别判断 session 过程流与 run 通知流的结束，不以网络 EOF 代替业务终态或保存状态。按 D76 收到 stream_end 后停止该订阅的重连，未收到即意外断开按中断处理；该控制通知不新增业务终态或持久化记录。页面关闭订阅只中止网络连接，不调用 cancel；用户显式停止分析仍走 run cancel API。

M3 交付后端 HTTP/SSE 契约、文档和可验证的响应；M9 在前端重构时实现客户端并做端到端验收。具体 SSE 解析库留到前端实现时按届时依赖情况选择，本阶段不冻结库名或引入前端兼容层。

承接位置为 `M9-C08`，验收包括 HTTP 分支、事件跨网络分块、run 最新快照同步、session Last-Event-ID 续传与去重、两流正常结束和断连不取消。已同步父目录前端接入约定。

适用：`M3-C15`、`M3-A08`、`M9-C07`、`M9-C08`、`M9-A05`、`M2-C01`–`M2-C03`、`GLOBAL-C10`。

### D19：全部完成条件满足后，默认保留 live state 60 秒

live-state 清理宽限期默认 `60` 秒，可通过后端配置调整。以下条件全部满足后才开始计时：

- session 已提交终态；
- workflow 已完全 quiesced，不再产生业务工作；
- 本 session 所有必需且适用的数据已确认 durable commit，包括终态事件、错误、存在时的结果，以及适用的晚到审计和收尾记录。

持久化失败时不开始计时；补写完整且其余条件满足后，重新获得完整的 60 秒保留窗口。计时用于清理内存，不延迟按 D04/D16 交付终态或结果。`completed_with_persistence_error` 后补写恢复也遵守该保留窗口，不改写其原终态。

实际清理前必须再次检查资格；出现新的未确认必需写入时不得沿用已失效的“全部持久化”确认直接清理。计时和清理调度不得占用 per-session 状态/event 临界区。

完成清理后，新 SSE 握手按 D17 返回 `410` 并转历史读取；历史数据和幂等记录继续保留。前端按实际接口响应处理，不用本地倒计时推断后端已清理。

配置字段与校验、开始计时后资格变化的具体处理、cleanup callback 失败的重试方式仍需细化。SSE 正常终态关闭和清理按 D20 执行。

适用：`M3-C12`、`M3-C13`、`M3-C15`、`M3-A06`、`M3-A08`、`M2-C04`。

### D20：清理按正常 SSE 结束流程实施，控制设计范围

原单流设计在发送业务终态后关闭 SSE，后续已由 D70 替代：session 结束并发完可见过程后关闭，run 通知流则等待业务终态、执行收敛和必需写入全部确认，不再等待 grace。D19 的清理门槛与默认 60 秒保留不变，实际清理后的新连接按 D17 转历史查询。

用户明确要求不为极少出现的“60 秒后旧 SSE 仍未发完”单独设计。撤回前轮提出的专用只读快照/独立读取所有权方案，不增加浏览器已读确认、等待慢连接排空或延长保留期的机制，并从 M3 专项验收中移除该极端竞态。普通 SSE 终态关闭、断连释放请求资源、持久化门槛和 `410` 历史入口仍按既定契约实现。

这项取舍在 M3 当前范围内结束讨论，不另建专项延后任务。后续对齐优先集中于 transcript 内容、持久化和历史接口的正常使用需求。

适用：`M3-C12`、`M3-C15`、`M3-A08`。

### D21：按水体进入预测与推理上下文，展示规则独立于存储大小

用户明确的产品流程如下，地图和最终前端由 M9 实现：

1. 分析完成后，每个实际参与推理的水体都显示在地图上。
2. 点击某个水体，显示它的预测结果，包含分时段预测、总体预测值，以及推理概述和总结。
3. 从预测结果的入口进入对应的具体推理流程，呈现类似 Codex 的上下文阅读体验。
4. skill、tool、hook 等内容按语义分块，默认折叠，用户主动点击后展开具体内容；与块的字节大小无关。

D44 补充历史入口：用户从分页的 query 历史列表选择某次分析，恢复当次地图标点、连线，再点击水体进入上述多层会话展示；Agent 过程本身不提供分页展示。

M3 的大内容策略只负责 transcript 完整保存、数据库中的内容组织和接口按需装载。inline 上限、preview 和 reference 不能成为前端自动展开规则。完整内容可在独立记录中保存；是否已经随响应返回，与是否在界面展开是两回事。后续 D23 已确认默认 `64 KiB` 内联上限与 `2 KiB` 预览正文上限，二者仍不决定产品折叠状态。

当前 M1 已有 `InferenceResult.target_comid/result_id/series/analysis_detail`、`AnalysisDetail.summary/steps/transcript_item_refs` 和 `AnalysisStep.transcript_item_refs`，可以承接“水体结果 → 分析详情 → transcript 内容”的关联。M3 保存稳定 item identity、类型/版本、顺序与完整内容引用；M6/M7 产生真实结果和推理过程时补齐关联，避免前端靠解析日志或猜测文本确定水体归属。具体 transcript envelope 和查询映射仍需定型。

用户已明确“总体预测值”指跨多个参数的综合水质指标。当前 `overall_confidence` 是置信度，不能代替该指标；现有模型也没有对应的综合指标字段。具体采用哪种指标、计算口径及缺失参数处理由 `M6-C14` 定型，并提供可追溯的结果依据；M3 不临时创造指标或把 preview 文本当作推理总结。

阶段责任：M3 提供持久化与按需读取基础；M6 定型真实预测、综合水质指标、概述/总结及结果到 transcript 的引用；M7 保留所有参与水体的结果与对应过程；M9 实现地图、结果面板与语义折叠。skill/tool/hook 区块由真实发生的操作记录驱动，不因 UI 设计而在 M3 伪造执行记录或新增不必要的执行框架。

已同步父目录前端接入文档及相关跨 milestone 契约。适用：`M3-C02`、`M3-C04`、`M3-C05`、`M3-C08`、`M6-C10`、`M6-C13`、`M6-C14`、`M7-C08`、`M9-C08`、`M9-C10`、`GLOBAL-C09`、`GLOBAL-C10`。

### D22：单份 session transcript，按水体与调用关系关联读取

术语修订：按 D50，本节原“session transcript”指整次 run 的记录集合；每个水体 Agent 实际拥有独立 session，上下文与消息归属必须分开。记录可统一存储并引用公共内容，不能把独立 session 降格为同一上下文的展示过滤。

一次 run 保存统一的原 transcript 记录集合，各独立 session 保留自己的消息归属；沿用 D08/D56 的 run 内 `transcript_sequence` 追加顺序，不为每个水体复制完整过程或重新编号。

水体推理记录明确关联 COMID。工具调用的开始、结束及相关 hook 通过稳定调用 ID 关联，读端可以将同一次操作组织为可折叠区块；不能仅凭工具名称、相邻记录或文本猜测配对关系。

每个水体的结果关联该水体的完整推理记录，不能只保留最终总结引用的少量步骤而丢失其余上下文。session 公共上下文保留公共归属，通过引用关联到需要它的水体，完整内容只保存一份。`AnalysisDetail` 和步骤引用继续用于结果溯源，不另存一套含义不同的 transcript。

第一版按 session 与水体 scope 一次取得该水体全部过程记录，再解析其中的显式引用、读取适用的公共上下文；按 D45，不分页或截取末尾若干条，未被总结引用的记录也须保留。引用继续保存在原 typed content 及已有 AnalysisDetail/AnalysisStep.transcript_item_refs 中。D33 延后关联索引表，不延后这套引用保存、校验和完整过程读取能力。

M3 定型记录身份、归属、调用配对及公共内容引用的存储/读取能力；M6/M7 产生真实水体结果与操作时填入真实关联。当前阶段没有的 COMID 或调用记录不伪造。公共字段命名与职责按 D29，Agent/操作身份按 D32；数据库关联约束和完整查询 DTO 在 schema/API 设计中补齐。

使用事件类型、水体 COMID 和稳定调用 ID 显式关联记录；关联字段保持明确含义。本决策不改变 D21 的语义折叠规则，也不决定 inline/preview 的大小。

适用：`GLOBAL-C03`、`GLOBAL-C09`、`M3-C01`、`M3-C02`、`M3-C05`、`M3-C16`、`M6-C10`、`M6-C12`、`M7-C08`、`M9-C10`。

### D23：默认 64 KiB 内联，超出后完整保存并返回 2 KiB 预览

单条脱敏后内容按实际 UTF-8 编码大小判断，默认规则如下：

| 内容大小 | 持久化组织与 timeline 读取 |
|---|---|
| 不超过 `64 KiB`（65,536 字节） | 内容内联保存，timeline 返回内联内容。 |
| 超过 `64 KiB` | 完整内容保存到同一 PostgreSQL 的独立内容记录；timeline 返回完整内容引用、完整字节数和截取预览。 |

预览正文默认总计最多 `2 KiB`（2,048 字节），首尾各最多 `1 KiB`，保留完整 Unicode 字符并明确标注中间省略。预览是文本片段，不作为完整 JSON 或真实推理总结解析；完整内容通过引用按需读取。标注和引用属于响应元信息，不冒充原内容。

内联上限与预览正文上限均可配置，配置项及示例纳入 D06 的跨环境配置交付。阈值只控制内容存储和接口装载，不裁掉完整内容、不改写 Agent 输入，也不决定前端折叠状态；已内联的 skill/tool/hook 仍按 D21 默认折叠。

本设计将全文与预览分离，使用 PostgreSQL 内容引用，预览按 UTF-8 字节上限截取。该存储策略不改变传给 Agent 的工具输入或输出。

适用：`M3-C02`、`M3-C05`、`M3-C06`、`M3-A03`、`M9-C10`、`M9-A07`。未完成持久化时的读取方式已由 D24 确认，引用与全文的一致提交按 D25 执行；具体路由及读取 DTO 继续细化。

### D24：当前结果与上下文统一读取，后端选择内存或数据库来源

当前分析的结果和上下文按 D42 使用合并后的读取路径，默认自动选择来源，前端沿用 D57 的同一组 run/item 全文引用：

| 状态 | 当前分析读取来源 |
|---|---|
| live state 仍在内存中 | 从内存读取当前状态、已产生的结果和完整上下文，包括尚未完成持久化的大内容。 |
| live state 已按 D19 清理，或服务重启后不再存在 | 同一入口读取 PostgreSQL 中的已保存内容。 |

后端负责选择来源，前端不用判断何时切换到数据库，也不用替换原内容引用。读取内存不依赖数据库当前可用；读到结果或全文不等于它已经持久化。尚未完整保存时按 D40 明确返回保存状态，存在当前保存错误时携带安全 warning；正常等待不伪造失败/error_id。前端按 D01/D04/D38/D40 展示结果和保存信息；completed 也可能在终态选定后遇到写入失败，不能单靠业务状态判断保存完整。补写恢复不改写原终态或发布第二个 terminal event。

历史查询仍按 D10 只返回 PostgreSQL 已持久化事实，不能混入内存内容并宣称已保存。按 D33/D45，当前与历史读取共享 DTO、内容类型/版本解析、全文装载和完整有序记录装配；来源选择、可见性及错误处理由各自的读取语义明确约束。引用解析也使用所选来源，历史入口不回退到内存补齐缺失内容。数据库读取失败按既有错误契约返回错误，不伪装为空内容。

内存保留及清理门槛继续遵守 D19；进程在补写前退出后未落盘内容可能丢失，沿用 D01 的已接受边界。实时读取不绕过取消后的晚到结果传播限制；这类内容仍只用于既定历史审计。D17 的 SSE 终态关闭及 `410` 转历史规则保持原义，不由本读取入口恢复或重新执行分析。

实时输出与持久化查询分别承担交付和历史读取职责。M3 通过统一读取入口、稳定内容引用和持久化状态表达，支持内存优先与释放后的数据库读取。

适用：`M3-C01`、`M3-C04`、`M3-C05`、`M3-C10`、`M3-C11`、`M3-C12`、`M3-C17`、`M3-A07`、`M9-C10`。保存运行信息按 D40，统一读取路径和自动默认行为按 D42，历史读取的显式选择按 D43，完整过程装载按 D45；完整响应 DTO 继续细化，分页仅针对 query 历史列表。

### D25：每批 transcript、完整内容与关联原子提交

运行过程仍按 D03 增量追加；同一 run 的每批追加使用一个短 PostgreSQL 事务，一起保存该批 transcript item 元信息、新增的完整内容及原 typed content 中的显式引用。已有公共内容通过引用复用，不重复保存全文。第一版没有独立关联表，引用随其所在正文原子保存；写入边界按 D58 校验引用身份、所属 run、适用 session 和目标存在性，普通过程关联允许同 run 内跨 session。

状态由现有状态机统一决定，存储接收它产生的状态快照和适用记录。存在相应完成/失败/取消等过程记录时，session 状态更新与记录追加在同一数据库事务中保存。running 没有公开事件时仍持久化状态快照，不为了数据库投影增加事件或回放重建机制。异步写入允许数据库暂时落后于 live state，取消立即响应、终态竞争和 D04 补写预算继续遵守原契约。

数据库中整批生效或整批不生效；写入步骤失败则回滚事务，不能留下已提交的 item 却缺少本批对应全文或关联的半成品。确认数据库提交成功后才确认该批已持久化，事务内部回调、入队或写入 live buffer 不算提交成功。单批成功不等于整个 session 的全部必需写入都已完成，清理仍按 D19 判断。

补写保留原 item、完整内容和关联身份，继续使用 D04 的统一重试预算；不重新运行分析。未收到提交结果不等于数据库已回滚，仍需按稳定身份核实，不能以新 ID 再造一批事实。

全文、transcript 和正文引用统一在 PostgreSQL 中提交，适用的 session 状态与查询字段更新纳入相应事务。M6/M7 以后如因真实查询需求建设关联索引，它必须从原引用生成，并与对应记录同批提交；M3 不预建该索引。实际提交成功才算持久化确认。

本决策冻结增量追加的完整性边界，单次写入预算按 D36，组批与触发方式按 D37，终态选定与 cancel 的边界按 D38。表结构与约束、提交结果核实的具体操作继续细化。

适用：`GLOBAL-C09`、`M3-C01`、`M3-C05`、`M3-C12`、`M3-C16`、`M3-C18`、`M3-A03`、`M3-A10`。

### D26：日志保留 query 正文，仅对其中凭据脱敏

用户明确修正前轮方案：日志不需要隐藏 query。业务分析 query 不自动视为 secret，可以作为日志正文或结构化字段保留；其中的 API key、Authorization、Cookie 等凭据仍按 GLOBAL-C07 脱敏。不能因字段名为 `query` 就替换整段内容，也不能将完整 query 注册为异常诊断的私有值并一并抹除。

日志与 transcript 均需保留可审计的业务正文，凭据使用明确脱敏标记。日志不替代 transcript 的历史事实源。该决定针对业务分析 query，不要求记录完整 HTTP body/headers 或改用原始 URL 访问日志；已有 request/session/error ID 和 route 模板继续用于关联排障。

当前 M2 代码仍采用旧行为：`redaction.py` 将 `query` 纳入整字段/赋值脱敏，HTTP 和 workflow 错误路径将完整 query 传入 `redaction_values`，formatter 也尚未选择独立 query 字段。M3 实现必须一起调整这些入口、记录字段及对应日志回归；仅从正则中移除 query 不能视为已完成。具体记录点与日志级别在实现设计中定型，本次没有修改运行时代码。

M2 文档保留现有实现和当时测试证据，并注明由本决策取代后续的“日志禁止 query”约束。新增验收应覆盖普通 query 原文和包含凭据的 query：正常正文仍可辨认，凭据在结构化字段及异常诊断中均被移除。已有 URL/Authorization/Cookie 等凭据保护不因这一调整失效。

请求正文可用于诊断；凭据识别可结合已知凭据值与明确敏感模式。日志仍按本项目字段与脱敏规则记录，不以整对象打印或图片数据替换代替凭据脱敏。

本决策确认日志 query 的保留规则；统一 transcript 记录入口与持久化边界的脱敏位置已在后续 D27 确认。

适用：`GLOBAL-C07`、`GLOBAL-C09`、`M2-C09`、`M3-C06`、`M3-C19`、`M3-A11`。

### D27：进入可读取的 live buffer 前脱敏，持久化边界再次执行

统一 transcript 记录入口先对凭据脱敏，再将记录放入可供 D24 读取的 live buffer；持久化边界再次强制执行同一规则，不能仅依赖调用方已处理的约定。

普通 query、prompt、工具数据和推理正文保留；识别出的 API key、Authorization、Cookie 等凭据使用明确的 `[REDACTED]` 标记。preview 和字节数从脱敏后的内容生成，内存读取与持久化使用同一份安全记录，完整内容引用不得绕过脱敏。规则需支持重复执行，不使已经安全的业务正文在写库时产生另一种含义。

识别可参考已知运行时凭据值、明确敏感字段和凭据文本模式，不能直接复制当前日志模块整段隐藏 query/request body 的策略。日志 query 按 D26 保留正文；业务原始输入与凭据在执行侧的使用职责不因 transcript 脱敏改写。

根据 GLOBAL-C07，脱敏失败不得将原文作为 fallback 返回前端、写库或打印到日志。现有日志 formatter 已有固定安全错误输出，可参考该失败边界；transcript 的具体错误模型、类型校验配合、凭据来源及失败传播在实现设计中补齐，不将其视为普通数据库补写即可修复的问题。

凭据识别采用已知凭据值与明确敏感模式，在上述两个入口实施同一规则，不引入通用 DLP 框架。

适用：`GLOBAL-C07`、`GLOBAL-C09`、`M3-C02`、`M3-C05`、`M3-C06`、`M3-C17`、`M3-A03`。两个处理位置已确认，具体规则与类型化模型的衔接继续细化。

### D28：M3 首批注册四类明确 schema 的内容

M3 生产路径先支持以下四类 transcript content，按 `content_type + content_schema_version` 选择对应 schema 并严格校验：

| content_type | 内容职责 |
|---|---|
| `analysis_request` | 用户的业务请求，保留 query 等真实输入，凭据按 D27 脱敏。 |
| `lifecycle_event` | 复用原 LifecycleEvent，包括创建、完成、失败、取消及其原版本、时间和 sequence。 |
| `error` | 未由生命周期事件完整携带的独立错误事实。 |
| `runtime_fact` | workflow 已收尾、持久化已恢复等内部事实；每种 fact 的判别值和字段也须明确校验。 |

创建配置由原 `session_created` item 完整固化，读取 session DTO 时可从它组装 configuration；analysis_sessions 不再额外保存完整配置，也不追加同义 `configuration_snapshot` item。D13 的小型不可变创建回执只用于返回原创建响应。生命周期事件已经完整携带的错误通过原记录引用定位，不再复制成另一个 error item。

LLM、tool、skill、hook、真实分析 context 和 final result 的内容类型由实际产生它们的后续 milestone 扩展注册，继续使用同一存储、版本处理与读取能力。M3 不预造尚未存在的业务 payload；对存在时的版本化 result 存储能力，用测试专用注册类型验证，生产路径不注册 fake result。不改变 M3-C04/M3-C08 的 final-result 接力要求。

`runtime_fact` 不能作为任意 JSON 的写入入口。新写入未知类型或版本仍按 D09 拒绝；历史未知版本继续保留原身份并明确呈现无法解析。公共 envelope 按 D29；具体各类型字段在后续 schema 设计中收敛。

按内容类型使用独立的 payload 模型，配合版本和严格校验，不使用任意 Object payload 作为生产内容契约。

适用：`GLOBAL-C09`、`M3-C02`、`M3-C03`、`M3-C04`、`M3-C08`、`M3-A01`、`M3-A02`、`M6-C10`、`M6-C11`。

### D29：公共 envelope 的字段命名与职责

每条 transcript 使用以下公共字段，内容类型仍按 D28 注册：

| 字段组 | 字段与职责 |
|---|---|
| 身份与顺序 | 按 D50/D52 保留所属 run、适用 session 与 `item_id` 身份；`transcript_sequence` 按 D56 在 run 内统一分配，具体 DTO 层级继续定型。 |
| 发生时间 | API 使用 `occurred_at`，统一 UTC，替代早期清单中的泛化 `timestamp`；按 D55 从数据库 `created_at` 装配，不独立存列。生命周期 item 须与原事件发生时间一致。 |
| 类型与版本 | `content_type`、`content_schema_version`，共同确定内容校验与读取方式。 |
| 业务归属 | `scope` 容纳适用时的 `target_comid`、`operation_id`；Agent 归属统一使用 D52 的 `session_id`，不保留同义执行 agent_id。run/session 身份在 DTO 中的具体层级继续定型，公共记录不伪造水体或操作归属。 |
| 请求与错误关联 | `correlation` 容纳适用时的 `request_id`、`error_id`，与业务 scope 分工明确。 |
| 内容读取 | 内联 `content` 或完整内容 `content_ref`，两种装载表示互斥；大内容附 preview 和完整字节数，遵守 D23。 |

`content_type` 是外层记录类别的唯一判别字段，不再另加含义重复的外层 `type`。内容中原 LifecycleEvent 的 `type`、schema version 和 sequence 保留原义，不能在统一 envelope 时删掉或重命名它们。

水体与操作归属只填真实适用的值，公共上下文通过 D22 的引用关联。`tags`、`rag_eligible`、`provenance`、`confidence` 按 D30 保留真实业务元信息，不为无依据的请求或生命周期记录伪造置信度和来源。

采用精简公共 envelope 与分类 payload，以明确的 scope 和 correlation 表达归属与排障关联。本决策冻结公共字段命名与分工，尚未冻结 PostgreSQL 表列、索引、ID 约束和所有读取 DTO。

公共 envelope 描述领域/返回语义，不要求每个对象都原样另存 JSON。按 D33，scope/correlation 的查询成员落列后在返回时组装对象；content_ref 按 D57 从原 run_id + item_id 组装，数据库不重复保存引用对象或 URL。正文已有的 confidence/provenance 按注册类型提取，不由调用方再独立填写一套同义值。

适用：`GLOBAL-C03`、`GLOBAL-C09`、`M3-C02`、`M3-C05`、`M3-C08`、`M3-C16`、`M3-C17`、`M3-A02`、`M3-A09`。

### D30：元信息采用明确默认值，保留真实业务依据

| 字段 | 已确认填充规则 |
|---|---|
| `tags` | 默认空列表，仅辅助筛选；真实分类由记录生产方提供，不代替水体归属、content_type 或业务状态。 |
| `rag_eligible` | 默认 false。M3 首批请求、生命周期、错误、内部事实记录不自动进入 RAG；后续业务生产方依其资格规则显式标记，M8 消费该标记。保存成功不代表可进入 RAG。 |
| `confidence` | 有真实业务置信度时保留原值，按既有领域约束校验 `[0,1]`；不适用或未知时为 null，不用 0 或 1 作为默认判断，M3 不额外打分。 |
| `provenance` | 有真实来源时保留可追溯的原信息；没有适用来源时为 null，不伪造 provider、来源 URL 或检索时间。 |

元信息不替代业务 content 内已有的结果、证据和来源事实。正文已有 confidence/provenance 时，由该类型的统一解析/提取规则提供返回值；仅出现明确筛选、排序或检索需求才增加派生列，并从同一事实生成。不能让调用方分别填写正文和元信息，也不能把 overall_confidence、参数置信度、时间窗 confidence 或 evidence confidence_hint 混为同一层级。无适用的单一值时公共字段保留 null，正文中的各层级真实信息仍完整保存。具体来源结构、多来源映射由对应业务类型明确。

tags 默认空、rag_eligible 默认 false 的语义继续保留，作为适用的 item 元信息保存；实际业务类型已有同义资格字段时须明确唯一来源，不能双向独立维护。`rag_eligible=false` 仅表示该记录不作为 eligible item 进入 RAG，不限制用户正常读取历史或按水体查看过程。

本项目 EvidenceFragment 已采用 rag_eligible 默认 false 和可空 confidence_hint，可沿用其默认值思路；证据 provenance 仍按领域规则保留。

适用：`GLOBAL-C06`、`GLOBAL-C09`、`M3-C02`、`M3-C07`、`M3-A02`、`M5-C02`、`M6-C10`、`M8-C01`、`M8-C04`、`M8-A01`。本决策确认字段默认值与填充原则，具体 RAG 资格算法仍由相关业务阶段定型。

### D31：UUID 标识 item，全文引用原 item

| 身份 | 已确认规则 |
|---|---|
| `item_id` | 后端在记录首次创建时生成 UUID，数据库中全局唯一；D81 明确流式消息在开始生成时分配，片段与最终正文复用；补写、重读、前端展开保留该身份，不从内容文本计算 ID。 |
| `transcript_sequence` | 按 D56 表示 run 内统一追加顺序；session 读取保留筛选后的原序号，不另维护局部编号。不作为 item_id，也不按 UUID 排序，D45 不以它提供 Agent 记录分页。 |
| `content_ref` | 按 D57 统一定位原记录的 run_id + item_id，通过 D24 的统一内容入口读取全文，不为同一 item 的完整内容另设公开 content_id。 |
| 引用校验 | 全文读取核对 item 确实属于指定 run，session_id 继续表达适用 Agent 归属；D58 允许同 run 内跨 session 的普通过程引用，跨 run 证据使用明确历史来源。公共上下文复用原 item，内容相同但独立发生的记录仍使用不同 ID。 |

统一全文入口也能读取原本内联保存的 item，不依赖内容位于内存、数据库内联列还是独立内容记录。D23 的 inline/reference 只控制返回装载，D25 的原子追加和补写保留原身份，D22 的结果/步骤引用继续定位同一份过程。

创建记录时生成 UUID，可沿用本项目已有 session 的 uuid4/id_factory 组织方式。对外全文引用按 D57 使用 run/item 身份，不暴露底层文件路径。

适用：`GLOBAL-C09`、`M3-C01`、`M3-C05`、`M3-C16`、`M3-C17`、`M3-C18`、`M3-A01`、`M3-A03`、`M3-A10`。全文 URL 按 D65，具体 content_ref DTO 和数据库约束继续细化；agent/operation 身份按 D32。

### D32：水体身份与 Agent、操作执行身份分开

本节按后续 D52 修订：原先标识一次 Agent 执行的 agent_id 合并到新模型的 session_id，水体和调用身份仍保持各自职责。

| 身份 | 已确认规则 |
|---|---|
| `target_comid` | 真实水体的业务身份，可在多次分析中重复出现。 |
| `session_id` | 按 D52 标识一个 Agent 的独立上下文和一次完整执行，由后端创建 UUID；同一执行的全部记录关联它，新的执行生成新 ID，不直接拿 COMID、角色或 Agent 名称充当执行身份。 |
| `agent_role` | 表达问题解析或水体推理职责，不作为唯一执行身份；角色的具体枚举编码随 DTO 定型。 |
| `operation_id` | 标识一次模型/工具等调用，由后端创建 UUID；该调用的开始、结束及直接关联的 hook 记录共享它。新的调用生成新 ID，不直接把工具名称或模型返回的 tool_call_id 当作全局操作身份。 |
| 模型原始调用 ID | 如有 tool_call_id，保留在对应类型的 payload 内，用于还原模型协议和追溯；不因系统 operation_id 而改写。 |

读取与数据库补写不创建新的 session/operation ID。适用的归属在真实执行开始时建立，M3 只保存/校验关联，不因 schema 而启动尚未实现的 Agent 或调用；业务调用的内部 attempt/nesting 细节由后续生产阶段定型。

按本项目的 session/水体执行语义分配稳定身份，并用操作 ID 显式关联记录。前端使用后端给出的 ID 组织操作，不从名称、COMID 或正文推导执行身份。

适用：`GLOBAL-C03`、`GLOBAL-C09`、`M3-C02`、`M3-C16`、`M3-A09`、`M6-C12`、`M7-C08`、`M9-C10`。数据库关联约束与读取 DTO 继续在 schema/API 设计中补齐。

### D33：三张核心表，减少重复存储并复用读取实现

修订状态：本节的三表结论产生于把整次分析称为 session 的旧模型，现由 D50–D53 的两层领域模型与四表职责替换。减少全文副本、查询投影同源、状态/适用记录原子提交、公共内容复用和不引入事件回放框架的原则继续保留。

四张核心表的当前职责统一见 [D53](#d53四张核心表会话状态与两层记录归属)，本节继续说明去重与原子性约束，不再维护旧三表字段清单。

#### 内容归属与允许的少量快照

analysis_runs 与 analysis_sessions 不复制完整请求、完整配置、完整结果或整段 transcript。run 列表确实需要的少量字段从同一业务事实生成，不能两边独立赋值和修改。完整配置以原创建事件为读取来源，历史列表已约定的 configuration 字段仍可据此返回；API 返回表示按原事实装配，角色与水体归属优先从所属 session 取得。

一个 run 最多对应一个创建 key，幂等信息与 run 同期保留，放在 analysis_runs 中，不建设独立 analysis_creation_keys 表。key 的格式和数据库唯一范围按 D34；无 key 时继续允许独立创建。原请求体指纹仍在规范化前计算，完整业务请求仍经脱敏后保存，不能以保留指纹为由另存未经脱敏的原始 body。

原创建回执是为稳定重试响应而保留的一份小型不可变快照，从首次创建响应一次捕获，与创建信息同事务保存；重试不从当前状态、当前默认配置或后来变更的响应结构重建它。即使回执包含必要配置，也不再增设另一份同义创建快照或配置维护入口。D11–D16 的新 key/原样重试、409、原 201、并发唯一创建和不重新执行的行为均保留。

#### 显式引用与完整过程读取

M3 暂不建设 transcript_item_links。显式引用继续保存在原 typed content，以及已有 AnalysisDetail、AnalysisStep 的 transcript_item_refs；引用提取由对应注册类型负责，不搜索任意文本猜测 ID。

按水体读取先定位所属 run 下的独立 session，按 D45 以 transcript_sequence 升序一次取得该 session 的所有过程记录，再读取其中显式引用的公共上下文及其必要引用。公共记录按 D53 保留在原 run 或 session 中，不转移到问题解析 session，也不复制到各水体 session。通过 item_id 去重并保留原身份/顺序；最终总结或 AnalysisDetail 挑选的引用不作为过程全集。大正文中的引用须从完整已校验内容提取，不能从截断 preview 解析。此时服务器可以为解析引用装载必要全文，前端仍按原 inline/preview/reference 契约按需加载。

存储写入时按 D58 校验引用身份、所属 run、适用 session 和目标存在性；普通过程引用限于同 run，可跨 session，目标须已保存或与引用它的记录同批保存。当前 live 读取在其来源和可见性范围内解析引用；历史读取只使用数据库中已保存的目标。目标缺失或错误归属须明确报错，不能静默漏掉相关上下文。完整内容仍只保存于原 item；同一 item 按 D23 选择内联或独立全文，两个位置不同时复制全文。

M6/M7 出现真实关联查询、反向查询或性能需求时再评估关联索引，归属 M6-C10/M7-C08；没有需求时继续使用 scope + 原引用读取。若建设 transcript_item_links，它必须从原引用生成、与对应记录同批提交，不接受独立业务编辑，且应以同一组真实过程验证建索引前后读取结果一致及失败回滚。M3-C16/M3-A09/M3-A10 的引用保存、校验、复用与完整过程验收继续由 M3 承接。

#### 存储列与返回对象

| 信息 | 唯一来源与装配方式 |
|---|---|
| content_ref | 按 D57 返回时从原 run_id + item_id 组装，不包含重复的 session 定位身份，不保存同义引用对象、URL 或额外公开 content_id。路径按 D65，具体 DTO 继续定型。 |
| scope / correlation | 从权威归属与查询列装配，不同时维护列和同义 JSON；角色及水体归属优先来自 session，不在每条记录中独立填充同义字段。 |

#### 共用读取实现，明确来源与可见性

当前与历史读取共享 DTO、内容类型/版本解析、全文装载和 D45 的完整有序记录装配。存储来源适配只负责取得记录与内容；不各自维护一套 transcript 模型或内容解析器。D45 调整此前共享 transcript 分页逻辑的要求，query 历史列表单独分页且只读数据库。

历史入口只选择 PostgreSQL，数据库故障返回错误，不能用内存补齐后声称已保存。当前入口在 live state 存在时使用内存，否则选择 PostgreSQL；同一组引用继续有效，持久化警告和取消后可见性限制必须在该读取语义下保留，不能因共用解析器而透出晚到结果。两种入口采用 D09 相同的类型/版本与损坏记录规则；统一路由和 view 按 D42/D43，完整读取 DTO 继续定型。

#### 当前状态由已有状态机维护

analysis_runs 保存整次分析当前状态，analysis_sessions 保存各 Agent 自身的必要状态与时间，transcript 保存原过程事实。既有 SessionCoordinator 对应 run 层状态维护，session 状态不能从 run 状态直接代替，具体枚举继续定型，通用时间列按 D55。各状态由对应执行流程统一维护，数据库持久化其快照，不通过扫描 transcript 再决定一遍状态。存在对应事件/记录时，如完成后的状态和完成事件，相关更新与追加在同一事务中保存。

现有 mark_running 更新 snapshot，而 _terminal_event 对 RUNNING 返回 None；M3 按统一规则保存 run 的 running 状态，不新增公开事件或通用事件回放框架。无对应记录的状态更新也属于必须确认的持久化工作。保存可暂时落后于实时状态，但补写不能倒退或覆盖已确定终态；唯一终态、取消即时响应及 D04/D19 的补写与清理门槛继续适用。终态选定、写入与 cancel 的边界按后续确认的 D38；D53 的独立 session 状态也遵守同一持久化确认原则，不重复维护同一层的状态逻辑。

#### 复核依据与验收归属

本仓库 SessionCoordinator 的 running 路径、AnalysisDetail/AnalysisStep 的显式引用，以及 EvidenceFragment、InferenceResult 中不同层级的置信度/来源字段，支持上述职责划分。一对一创建 key 按新模型与 run 同期保留，不需要独立受理生命周期；稳定指纹核对与相关写入事务分组继续适用。

本轮同步 M3-C01/C02/C03/C07/C09/C16/C17/C18 与 A02/A03/A04/A07/A09/A10，及 M6-C10/M7-C08 的按需索引责任。仅替换表、重复字段和重复实现要求；D04 重试、D25 原子提交、D31/D32 身份、D23 全文、D27 脱敏、D21 折叠、D05–D07 PostgreSQL 环境要求均保留。此前包含关联表外键的完整性候选方案不再作为第一版候选。

适用：`GLOBAL-C09`、`GLOBAL-C10`、`M3-C01`–`M3-C09`、`M3-C16`–`M3-C18`、`M3-A02`–`M3-A04`、`M3-A07`、`M3-A09`、`M3-A10`、`M6-C10`、`M7-C08`。去重与原子性原则按 D53 四表模型继续落实；具体列、索引、约束及读取 DTO 仍待后续定型，尚未创建数据库对象。

### D34：创建 key 使用 UUID v4，在同一数据库的创建接口内唯一

| 项目 | 已确认规则 |
|---|---|
| 客户端生成 | 每次主动提交生成新的随机 UUID v4，并在本次提交的重试中原样复用 key 和请求体。 |
| 后端识别 | 按 UUID 值识别 key；提供了请求头却不是合法 UUID v4 时返回既有校验错误格式的 `422`，不退化为无 key 创建。 |
| 唯一范围 | 同一套后端数据库的创建分析接口内唯一；当前创建接口没有用户或租户身份划分，不按尚未存在的 session_id 划分创建 key。 |
| 数据库保存 | analysis_sessions.idempotency_key 可空并带唯一约束；请求头省略时保存 null，允许多个无 key 的独立 session。 |

key 的 UUID 解析不改变 D12 的请求体匹配：请求体仍按原始字节计算指纹，不排序或重序列化。相同 UUID 值命中已有记录后按指纹返回原回执或 `409`；key 与 session_id、item_id、X-Request-ID 分别承担自身职责。格式有效也不代表创建已持久化，创建确认和启动仍按 D02/D15/D16 执行。

创建前尚无 session_id，幂等 key 由创建接口的数据库唯一约束保证；按已确认的 UUID 值处理，不增加字符串 trim 或其他规范化规则。

适用：`M3-C09`、`M3-A04`、`MR-G09`。本决策确认格式、唯一范围与非法格式状态码；创建等待按 D35，具体事务操作继续细化。

### D35：同 key 创建等待默认最多 5 秒

- 等待者等待正在进行的创建受理结果，默认最多 5 秒，可配置；同一次等待采用统一截止时间，锁等待和必要重读不能各自重新获得 5 秒。
- 在截止时间内确认提交成功则立即返回 D13 的原 `201`；确认回滚则按 D15 允许一个等待者接手。超时返回 `503`、`code=idempotency_wait_timeout`、`retryable=true`，使用既有安全错误响应。
- 等待超时只结束该等待请求，不取消创建所有者或已经创建的分析，也不宣称原事务已回滚；客户端仍原样复用 key 和请求体。
- 此值只约束同 key 等待，不是分析时长上限，也不是完整 HTTP 创建流程或所有数据库操作的统一超时。D04 的后台补写预算和失败后退避时机不变；单次数据库写入预算按 D36。

同 key 等待采用本项目确认的默认 5 秒上限，事务竞争与原回执重读共同遵守该期限。

适用：`M3-C09`、`M3-A04`、`M2-C04`、`MR-G09`。配置名称及数据库/应用层的截止时间落实方式继续在实现设计中明确。

### D36：单次数据库写入共用 5 秒执行预算

- 一次创建事务或 session 持久化批次的写入尝试，执行预算默认 5 秒、可配置；从开始获取连接起，连接等待、该批 SQL 和提交共用一个截止时间，不给每条 SQL 重新分配完整预算。提前失败就立即结束，不等待预算耗尽。
- 到期仍未确认提交则按本次写入超时处理并取消/收尾；保留未确认内容与原身份，不标记 persistence_confirmed。超时不等于已回滚，提交结果不确定时仍按 D02/D25 核实。
- 后台写入沿用 D04：本次失败/超时尝试结束后才开始 1/2/4/8/16 秒退避，最多 5 次重试；先完成旧调用的取消/连接收尾，不让同一 session 的写入调用并行，也不在 adapter 内加隐藏重试。收尾不重新获得一份执行预算，具体驱动实现及收尾界限还须落实。
- 创建写入未确认成功前不启动 workflow，也不套用后台的 5 次重试来延长创建请求。D35 同 key 等待仍有自己的截止时间；同一操作同时受两个截止时间约束时采用更早者，不能先等 5 秒再给同一次写入重新计时。

该预算不是整个分析的时长上限，也不替换 D04 的完成交付窗口。确认该批实际提交成功后才确认覆盖的写入，session 全部必需写入完成与清理资格仍按 D19/D25 判断。

5 秒是本项目确认的单次写入预算，覆盖连接等待、整批 SQL 与提交。

[PostgreSQL 超时文档](https://www.postgresql.org/docs/current/runtime-config-client.html)说明 statement_timeout 按单条语句计时，lock_timeout 只约束每次锁获取；它们不能独自代表包含连接等待的整批预算。[psycopg 异步操作文档](https://www.psycopg.org/psycopg3/docs/advanced/async.html#interrupting-async-operations)说明取消 Python task 不保证数据库操作未完成，因此必须保留提交结果不确定的既有处理边界。

适用：`M3-C08`、`M3-C09`、`M3-C11`、`M3-C12`、`M3-C18`、`M3-A04`、`M3-A06`、`M3-A10`。配置项、驱动收尾和提交核实的实现细节继续定型；本轮没有引入额外的自动重试层。

### D37：空闲即写、每 session 串行组批

- 有待写 item 或状态快照时，若该 session 写入器空闲就立即唤醒；没有待写内容时不轮询、不执行空事务，不增加专门等候合批的定时器。running 等没有对应 item 的状态更新也须触发写入。
- 每个 session 只有一个串行写入器，从 LiveTranscriptBuffer 的未确认内容与待保存状态中取得一批；写入期间产生的新内容留待下一批，不重新复制一套正文队列。
- 默认以 100 条 transcript item 为单批组批上限目标，可配置；已有不足 100 条也立即写，不等凑满。必须同事务成立的状态/事件、同批引用目标等作为完整一组处理，不能因计数拆散；单个原子组超过目标时独立提交整组。大正文仍完整保存，不按批次条数截断内容。
- 成功仅确认该批实际提交的内容和状态，再继续处理剩余内容；不能据此宣称整个 session 已保存完整。失败后保留已确定事实组成的原批次，按 D04 重试；新内容不抢跑、不打断退避、不重置预算。原批次恢复后再处理后续内容。
- 创建事务继续按 D02 单独确认后再启动；业务结束不等待合批定时器，但已有退避仍按 D04 执行。唯一终态的选定、最终写入与 cancel 的边界按 D38，不由组批逻辑提前决定终态事件。

记录产生后及时唤醒写入器，按 session 串行异步写入，保持 D03 的分析与落库分离；100 条是本项目确认的组批目标。

适用：`M3-C01`、`M3-C08`、`M3-C12`、`M3-C18`、`M3-A06`、`M3-A10`。配置项与具体批次表示继续在实现设计中落实；终态选定与最终持久化边界按 D38。

### D38：终态选定前检查既有写入，后续保存失败保留终态

成功分析结束时固定此前已经产生的必需结果、过程和状态的写入范围，包括没有对应公开事件的适用状态快照。该范围不包含尚未选定的终态及之后才产生的收尾事实；等待期间不因这些后续记录无限扩大判定范围。

- 在现有状态锁之外，按 D04 等待固定范围全部确认保存，或者第 3 次重试失败后的 2 秒交付窗口到期。窗口已在分析结束前到期时不重新等待；单批成功不代表固定范围已全部保存。
- 随后由现有状态机在短锁内根据实际确认情况一次选定 completed 或 completed_with_persistence_error，同时生成相应状态快照与唯一 session_completed，SSE、日志与 transcript 复用原事件。固定范围保存完整时选择 completed，窗口到期仍不完整时选择 completed_with_persistence_error 并附安全 warning/error_id；不把它们当作尚可替换的试写事件。
- 等待不阻塞显式取消。cancel 先被现有状态机接受就保持 cancelled，完成路径不再发布终态；完成先被接受则沿用已有终态冲突响应。锁内不等待数据库、退避或 workflow 收尾，不增加中间公开状态或第二套终态仲裁。
- 已选定的终态状态与事件仍按 D25/D37 作为同一原子组保存。它们自身或后续适用运行/收尾事实的写入失败，不改变已选定终态；当前统一读取返回持久化警告/error_id，保留未确认内容并按既定预算补写。不因产生终态而重置已有失败轮次，不发布第二个业务终态。D69 的 run SSE 另通知保存情况变化，其关闭时机按 D70，保存通知不改写原终态或原记录。
- completed 只表达业务完成，不能单凭它确认整个 session 已保存完整。D19 的清理门槛仍包括终态状态、终态事件及所有适用收尾记录的实际提交确认；固定范围保存成功不替代全部写入确认。历史只返回 PostgreSQL 已提交事实，数据库暂时落后于 live state 不得被掩盖。
- 后续补写成功仍保留原终态及事件中的原 warning/error_id，当前保存情况随实际确认更新，并按 D04 记录恢复事实；不改写当时发生过的终态。

本决策经用户确认收窄 D01/M3-C11 中“最终持久化失败”的判定范围：终态选定前检查固定范围，选定后的保存故障通过持久化警告表达。D04 的次数、退避和交付窗口，D25 的事务原子性，以及 D19 的全部必需写入清理门槛不变。

完成通知与保存确认分别表达业务和持久化事实；固定写入范围、唯一终态、失败补写和 cancel 规则由上述契约统一约束。

适用：`M2-C03`–`M2-C06`、`M2-C08`、`M3-C08`、`M3-C10`–`M3-C13`、`M3-C17`、`M3-C18`、`M3-A05`–`M3-A07`、`M3-A10`。读取中的保存运行信息按 D40；完整响应 DTO 及提交结果核实操作继续细化，没有改动现有后端实现。

### D39：自动补写耗尽后允许用户手动开启新一轮

- D04 的每轮最多 5 次自动重试耗尽后停止，保留未确认内容、live state 和安全错误关联；不因数据库恢复、刷新读取或新 item 到来而自行重置预算。
- 用户可主动触发“重试保存”，M3 提供接口，M9 在保存警告处提供入口。live state 仍在、仍有待保存内容且上一轮已经耗尽并停止时，由原串行写入器开启新一轮：立即进行首次尝试，失败后按 D04 最多自动重试 5 次，沿用 1/2/4/8/16 秒退避与 D36 的单次写入预算。这是明确的用户新操作，不是后台自动重启预算。
- 复用原 session、item、正文和失败批次，确认原批次成功后按 D37 继续后续待写内容；不重新分析、不生成新业务终态、不复制正文队列。补写已在执行或退避时，重复触发返回当前补写情况，不再启动写入器、增加并发尝试或重置预算。
- live state 已丢失时，不能靠此入口恢复未保存内容或启动分析；没有待保存内容时不执行空写入。触发成功只表示已开始或已有补写，不表示数据库已经保存成功。
- 原业务终态、原事件中的 warning/error_id、当前读取与历史来源边界继续按 D24/D38 执行。全部必需写入确认并满足其余条件后，才按 D19 开始完整保留窗口；用户手动恢复不绕过清理门槛，也不通过重新发布终态通知完成。

手动恢复复用既有保存入口和写入器，遵守有限重试预算；开启新一轮仍由用户显式触发。

适用：`M3-C12`、`M3-C17`、`M3-C18`、`M3-C20`、`M3-A06`、`M3-A07`、`M3-A12`、`M9-C11`、`M9-A08`。保存运行信息与按钮条件按 D40，手动补写路由及 HTTP 语义按 D41；当前未实现接口或按钮。

### D40：实时保存信息按读取来源生成，不另存重试状态

当前读取选择 live state 时，响应附一份 run 级 persistence 运行信息，由 live 中已产生但尚未定稿的必需正文、原写入器的待确认内容、实际提交确认与重试预算计算，不在 PostgreSQL 再保存一套可独立编辑的重试状态。该信息用于读取响应，D69 的 run SSE 也从相同事实生成保存变化通知；不改变原创建回执或已产生的生命周期记录。

| persistence.state | 含义与前端行为 |
|---|---|
| up_to_date | 当前已经产生的必需内容及状态更新均已确认保存；不保证未来内容，不单独构成 D19 的清理资格。 |
| pending | 已产生的必需内容尚未全部保存，包括等待消息定稿、待写入、正在写入或等待退避；不表示数据库正在执行写入，前端不通过按钮重置这一轮。 |
| retry_exhausted | 自动重试耗尽且已经停止，待写内容与 live state 仍在；前端可按 D39 显示“重试保存”。 |

persistence.warning 复用现有 PublicError 的 error_id/code/message/failed_stage/retryable 安全结构，没有当前保存错误时为 null。正常 pending 通过状态表明尚未保存，不伪造失败或 error_id；修复后当前 warning 可以消除，原终态事件中的 warning/error_id 仍按 D38 保留。按钮依据 retry_exhausted，不仅依据某个错误的 retryable 字段；读取不启动补写或重置预算。 D80 明确：生成中且尚未保存的正文也计入 pending，没有实际保存错误时 warning=null；已有 retry_exhausted 及错误优先保留，新片段不覆盖耗尽状态或重置预算。

历史读取及当前入口回退 PostgreSQL 时，persistence 为 null，表示本次读取不提供 live 保存运行信息；只保证返回的是已保存事实，不借内存推断整个分析已保存完整，也不通过 null 断言历史 session 当前一定没有 live state。原记录中已保存的错误/警告仍照常返回，不能因运行信息为空而隐藏。数据库读取失败仍返回错误，不借 null 掩盖失败或伪装为空历史。

当前与历史复用同一响应模型，persistence 只是按本次来源可用性生成的可空运行信息；不额外维护重复的 can_retry、重试状态行或另一套 transcript DTO。状态表达当前保存情况，不替换业务 status。D69 修订此前“不新增 SSE 通知、仅通过读取获知”的限制：run SSE 主动通知保存情况变化，GET 继续用于加载与核对，两者共用同一事实和语义。

业务状态与保存结果分别表达；三种实时保存状态、可空 warning 及历史 null 表示按本节定义，不另存一套运行状态。

适用：`M3-C12`、`M3-C17`、`M3-C20`、`M3-A06`、`M3-A07`、`M3-A12`、`M9-C11`、`M9-A08`。手动补写 HTTP 语义按 D41，统一读取路径和自动默认行为按 D42；完整读取响应结构继续定型，没有新增数据库字段或修改运行时代码。

### D41：手动补写接口只受理恢复，不等待保存完成

路由：POST /api/analysis/runs/{run_id}/persistence/retry。不需要请求体或创建分析的幂等 key；后端仅处理该 run 原有待写内容，不要求客户端重传正文，也不允许客户端指定另一批内容。

| 当前情况 | 响应与处理 |
|---|---|
| live 保存状态为 retry_exhausted | 按 D39 受理新一轮，返回 202 与 run_id、D40 persistence 快照。 |
| live 保存状态为 pending | 返回 202 与相同形状的响应，继续由原写入器负责；可等待消息定稿，也可已有待写、写入或退避，不新增写入器或重置预算。 |
| live 保存状态为 up_to_date | 返回 200 与相同形状的响应，不执行空写入。 |
| live state 不存在，数据库确认 session 仍在 | 返回 409 / persistence_retry_unavailable，retryable=false；说明当前没有可用于补写的 live state，可继续查看已保存历史。不能据此断言未保存内容一定丢失或整个分析已经保存完整。 |
| 内存、数据库均确认 session 不存在 | 返回既有安全 404。 |
| 查询数据库失败 / run_id 非法 | 分别沿用安全 503 / 422，不把查询失败伪装成不存在。 |

202 不等待本轮保存完成，响应只表达受理时的情况。状态检查、接受新一轮与响应快照在现有短同步边界内协调；不能并发开启同 session 写入器，不在锁内等待数据库。确实无法受理时返回安全错误并保留原待写内容，不能回复 202 却没有已受理的写入器负责处理。 若 pending 仅来自正在生成的未定稿正文，按 D80 继续等待消息结束或中断；不强制结束生成、不提前写入部分正文快照、不执行空事务，也不启动数据库重试。202 表示原写入器仍负责后续保存，不能据此声称数据库已经开始执行。

受理后的补写由原写入器负责，HTTP 断开不取消它。前端对此 POST 不自动重发；超时或响应丢失后先通过当前读取查看 persistence，需要再次开启新一轮时由用户主动操作。执行中的重复请求可以复用，并不意味着跨轮次自动重发也不会开启新一轮；第一版不为此增加独立操作 key、回执表或请求正文副本。

成功响应复用 D40 保存信息，仅包含 run_id 与 persistence，不复制完整 session/configuration/transcript；失败复用既有安全错误封装和 X-Request-ID。该 HTTP 操作不改变业务终态、不重新执行分析，创建接口的幂等规则保持原义。

按 D65 将已有取消动作的路由组织迁移到 /api/analysis/runs/{run_id}/cancel，无请求体的保存恢复动作同样归属于 run。[RFC 9110 的 202](https://www.rfc-editor.org/rfc/rfc9110.html#name-202-accepted)区分受理与处理完成，[409](https://www.rfc-editor.org/rfc/rfc9110.html#name-409-conflict)用于请求与资源当前状态冲突；本项目按上述表格选择响应并明确客户端不自动重发。

适用：`M3-C20`、`M3-A12`、`M9-C11`、`M9-A08`、`M2-C04`、`MR-G06`、`MR-G09`。该接口尚未实现；补写后的当前情况通过 D42 的默认自动读取取得，不能将设计接口当作已上线能力。

用户明确要求把此前候选中的当前/历史两组路径合并。同一种读取职责只保留一个路径，不建设 /current 路由族；session 详情、timeline 和单条全文仍按 D10/D23 分别按需加载。

D42 的统一来源原则继续适用；下表按 D50/D57/D64 和后续 D65 更新为 run/session 两层路径，替换旧整体 session 路径。完整目标路由见 D65，当前尚未实现。

| GET 路径 | 读取职责 |
|---|---|
| /api/analysis/runs | 沿用 D10 的数据库历史列表与分页。 |
| /api/analysis/runs/{run_id} | run 详情、存在时的原结果与会话简要信息。 |
| /api/analysis/runs/{run_id}/sessions/{session_id} | 所选 Agent 的详情与实际结果。 |
| /api/analysis/runs/{run_id}/sessions/{session_id}/transcript | 所选 session 的完整有序过程，保留显式公共引用。 |
| /api/analysis/runs/{run_id}/transcript/{item_id}/content | 读取原 item 的完整内容。 |

详情、timeline 和全文默认按 D24 自动选择：live state 存在时读内存，释放或重启后读 PostgreSQL。前端不用区分当前/历史路径、判断内存是否已释放或替换 D57 的原 run/item 全文引用。数据库内容仍是历史事实源，读取来源、D40 的 persistence 对象/null 和取消后可见性按对应语义处理，不能把内存读到的内容宣称为已保存。

共享 DTO、内容类型解析、全文装载和 D45 的完整记录装配；同一读取语义贯穿 timeline、全文及公共引用读取，不为两个来源保存重复引用对象或 URL。默认自动读取沿用当前读取的可见性限制，不因后端转读数据库而绕过取消后的晚到内容传播限制。

本决策将既有架构中详情路径的默认行为由历史读取调整为自动读取；D10/D33 已确认的“历史查询只返回 PostgreSQL 已保存事实”仍保留为独立读取语义，但不再要求独立路由。按 D43，通过同一路径的可选 view=history 显式选择历史语义，普通请求默认自动选择来源。

读取服务自动选择 live state 或 PostgreSQL，run/session 详情按新模型定型，全文沿用 D57 的稳定 run/item 身份。

适用：`M3-C04`、`M3-C05`、`M3-C17`、`M3-A07`、`M3-A09`、`M9-C07`、`M9-C10`、`M9-C11`。历史语义选择按 D43，过程完整列表按 D45；DTO、scope 筛选及 query 历史列表分页继续定型，没有修改 API 实现。

### D43：同一路径通过可选 view 选择严格历史读取

详情、timeline 与全文使用 D42 的统一路径，提供可选 view 参数：

| view | 读取规则 |
|---|---|
| 省略或 auto | 默认按 D24/D42 自动选择来源，live state 存在时读取内存，否则读取 PostgreSQL；普通结果页与手动补写后的读取无需传参。 |
| history | 同一路径只读 PostgreSQL 已保存事实，按 D40 返回 persistence=null，保留原记录中的错误和警告；不能退回内存补齐内容或实时保存状态。 |

session 列表沿用 D10 的数据库历史分页，不增加内存列表。SSE 410 引导的历史查阅使用统一路径的 view=history；历史入口的具体错误/引用 DTO 继续定型。数据库读取错误、未知/损坏内容及引用校验仍按原契约处理，模式选择不把失败解释成空结果。

单一路径通过 view=history 承接严格历史读取保证，普通请求沿用自动来源选择。

### D44：query 历史列表分页，按当次地图进入连续会话记录

### D48：历史游标编码位置，不保存分页状态

本设计采用时间与身份组成的明确排序边界，保持原 session 身份与 D47 的固定顺序，不引入新的持久化表或缓存副本。适用：`M3-C04`、`M3-A07`、`M9-C10`、`M9-A06`。本轮确认接口行为，尚未实现编码或读取逻辑。

### D50：run 覆盖整次分析，session 对应独立 Agent 上下文

用户明确的整体流程与领域边界如下：

1. 用户提交 query，包含问题、地点与时间，开启整次分析。
2. 问题解析 Agent 输出结构化需求，包括待查水质参数、坐标等。
3. 后端以目标水体为基准，向上游 BFS，寻找有水质数据的水体作为推理源头。
4. 依据水文网络组织有向无环图，从推理源头向目标水体推进，沿 DAG 在水体 Agent 间传递信息。
5. 每个水体 Agent 等待所有上游推理完成后只触发一次；从接收输入、调用外部能力获得证据到输出结果的整个 loop 是一个 session，具有独立上下文。
6. 从用户提交到各 Agent 输出结束的整体过程称为一个 run，历史列表分页展示 run。
7. 用户打开某个历史 run 后由前端展示地图；选中水体后查看其 session 的预测、总结与完整过程，继续使用既有多层展示和语义折叠。

| 概念 | 领域职责 |
|---|---|
| run | 一次用户提交的完整分析，包括解析、拓扑查找和各水体 session；承接此前整次分析的创建幂等、整体状态、SSE、取消、保存重试、清理及历史分页职责。 |
| session | 单个水体 Agent 的一次独立上下文与完整执行 loop，归属于一个 run，并关联该水体 COMID；同一 run 内该水体只触发一次。 |
| COMID | 水体业务身份，可在不同 run 中重复；不是跨 run 复用上下文的依据。 |
| transcript item | 原请求、配置、过程、消息、错误或实际业务结果的记录；应明确所属 run，以及适用时的 session，并保留稳定身份及原引用。 |

独立 session 是真实的 Agent 上下文边界，不只是前端水体视图。统一保存记录与公共内容复用仍可采用同一存储实现；各 session 的输入和上下文由业务流程明确组织，不能把整个 run 的所有水体消息直接作为一个共享 Agent 上下文。跨 session 的上游结果与公共记录关联须按新归属复核，旧的“所有引用必须属于同一 session”不能直接沿用为最终约束。

既有保存保证继续适用于整个 run：用户的新提交与幂等重试行为、原子提交、稳定 item 身份、脱敏、有限补写、持久化警告和完整过程读取均保留。D47–D49 的分页大小、固定创建顺序、无状态游标与仅分页参数的范围迁移到 run 历史；水体 session 的完整过程不分页。单个 Agent 的工具/模型调用仍可有自己的操作记录，保存重试不会重新触发水体 Agent。

当前代码的 AnalysisSession/SessionCoordinator 实际承担这里的 run 级职责。后续需要集中修订模型、API、schema、日志关联和契约中的身份命名；旧 M2 接口/事件文档保留为实现事实，不因本次术语明确而宣称代码已经迁移。D32 原 agent_id 已按 D52 合并到新 session_id；四表职责与两层记录归属按 D53 确认，路径按 D65、引用边界按 D58，具体列与校验实现继续定型。

参考实现中独立子会话拥有各自的消息和执行上下文，可以借鉴这种隔离方式；本项目按 run 组织完整分析、按 DAG 为各水体建立一次 session，不引入没有需求的多轮续聊或重复调度。

适用：`M3-C01`–`M3-C20` 中涉及整次分析身份的部分、`M3-A01`–`M3-A12` 的对应身份与归属验收、`M4-C01`/`M4-C06`–`M4-C08`、`M6-C12`、`M7-C01`/`M7-C08`、`M9-C10`/`M9-A06`/`M9-A07`。主流程与 run/session 含义已确认；问题解析 Agent 的独立 session 归属已由后续 D51 确认，最终存储/API 结构继续定型。

### D51：问题解析 Agent 也属于 run 下的独立 session

用户确认问题解析 Agent 也建立本次 run 下的独立 session。session 的通用含义扩展为单个 Agent 的独立上下文和完整执行 loop；问题解析和水体推理是两种不同职责，复用同一记录模型、内容解析与全文读取能力，不为解析过程另建一套 transcript。

- 问题解析 session 保存自己的输入、实际调用过程和结构化输出，会话本身不绑定水体 COMID；输出中真实解析出的目标 COMID、坐标、参数和时间需求正常保留。没有水体归属不能被误判为没有业务位置信息。

- run 的创建幂等、整体状态、保存重试和历史分页保持原约定，补写不会重跑任一 Agent。完整水体过程必须选中水体后展示；解析 session 的持久化与完整读取能力不自动规定新的前端页面或独立展示入口。

参考实现的独立会话消息与上下文隔离方式可复用到这两类 Agent；本次仅确认领域归属，不引入多轮续聊或额外会话调度。

按用户要求，从用户提问、问题解析、上游 BFS、DAG 调度、各 Agent 输出，到地图结果和历史记录阅读的完整主流程已写入 [总体设计第 1.1–1.3 节](../backend_architecture_skeleton.md#11-runsession-与水体的关系)。总体设计作为后续接力的流程入口，本文保留详细决策；路径按 D65，具体 schema、身份约束与完整状态 DTO 继续定型。

适用：`M3-C01`/`M3-C16`/`M3-C17`、`M3-A09`、`M4-C01`/`M4-A01`、`M7-C01`、`M9-C10`。本项已确认，尚未修改后端实现。

### D52：session_id 统一标识 Agent 执行，取消重复 agent_id

用户确认：在 D50/D51 的一次独立上下文对应一次完整执行模型下，原 D32 的执行 agent_id 与 session_id 职责重合，统一使用 session_id 关联该 Agent 的过程与结果，不再生成、保存或返回第二个同义执行 UUID。

| 字段 | 已确认含义 |
|---|---|
| run_id | 一次用户提交的完整分析，关联问题解析 session 与各水体 sessions。 |
| session_id | 单个 Agent 的独立上下文及完整执行身份，由后端生成 UUID；新的 run 中创建新的 sessions。 |
| agent_role | 问题解析或水体推理的职责，不能代替唯一执行身份。 |
| target_comid | 水体 session 绑定的水体业务身份；问题解析 session 不填写水体归属，解析输出里的目标 COMID 正常保存。 |

### D56：每个 run 统一分配 transcript_sequence

用户确认每个 run 只维护一套过程序号。run 自身记录、问题解析 session、各水体 session 及内部过程记录共同使用 run 内唯一、严格递增的 transcript_sequence，各 session 不再维护单独的 transcript 编号或计数器；D78 的 session SSE 续传编号不属于 transcript_sequence。

- 序号在原记录首次进入统一追加入口时确定；D82 明确流式消息在开始生成时进入该入口，和 item_id、created_at 一起固定，正文定稿时不再次追加编号。内存读取、保存、补写及历史重读保留原值，不按数据库完成写入或重试的时间重新编号。
- 并发 Agent 的记录可交错进入该序列；序号表达统一入口的追加顺序，不要求 Agent 串行执行，也不根据墙上时间二次排序。

参考实现显式保存并恢复消息之间的顺序关系。本项目已有统一记录入口与 run 范围的串行持久化，采用一套显式过程序号，避免额外维护每个 session 的消息顺序链或局部计数器；本项不引入状态事件回放重建。

### D57：全文引用统一使用 run_id 与 item_id

用户确认将旧 D31 的 session_id + item_id 全文引用调整为 run_id + item_id。所有原记录都属于一个 run，run 公共记录和各 Agent session 记录因此使用同一全文定位方式。

- content_ref 在返回时从原 run_id、item_id 组装，读取时核对该 item 确实属于指定 run；不能因 item_id 全局唯一而省略归属校验。
- session_id 继续保留在原记录的适用归属中，用于取得具体 Agent 的完整过程，不作为全文引用中另一套必需定位参数。公共记录不需要借用问题解析 session 身份才能读取。

参考实现的单条消息读取会同时核对消息 ID 与所属会话。本项目借鉴原记录身份和所属范围联合校验的方式，以 run 作为统一全文读取范围，覆盖公共记录及其下的独立 sessions。

### D58：普通过程引用限于同一 run，历史证据显式关联

用户确认普通过程引用允许跨 session，但必须属于同一 run；跨 run 信息通过 M8 的历史证据/来源结构明确关联。

- 普通 transcript_item_refs 可引用本次 run 的公共记录或其他 session 的原记录。例如，下游水体引用上游水体结果，或多个水体引用问题解析输出；目标正文留在原 item，调用方不复制全文或修改归属。
- 写入边界从 typed content 提取普通引用，核对目标属于相同 run、身份有效且目标已保存或与源记录同批保存。即使 item_id 全局唯一，也不能把其他 run 的记录作为本次普通过程引用静默接入；具体错误表示随 DTO 定型。
- 来自其他 run 的证据按 M8 的历史来源结构保存原来源身份、原置信度、类型/版本和检索信息。原记录仍可用其 run_id + item_id 读取；不能将它伪装成本次 session 产生的过程，或为了绕过边界而复制成另一条同义事实。
- 查询水体过程先取得其 session 的完整有序记录，再读取显式引用的公共上下文。普通引用允许跨 session 不意味着加载所有 session 的全部消息，也不以最终总结选出的少量引用替代完整过程。

全文定位与业务关联分别遵守 D57/D58：D57 校验所请求 item 属于引用中指定的 run，支持读取历史原 item；D58 校验普通引用的源与目标同 run，跨 run 则保留明确的历史证据语义。view、持久化警告与取消可见性仍按所选读取方式处理，历史不从 live state 补齐。

此处 stateless 的限制是不用其他 run 的历史记忆，本次 run 内上游 session 的结果仍是当前推理输入。memory_augmented 可在 M8 使用显式历史来源；本项不提前实现 RAG、新增关联索引表或复制原正文。

参考实现的单条消息读取校验其所属范围。本项目按多 Agent 流程把普通过程关联范围设为 run，同时保留 session 上下文隔离，并通过原有历史 provenance 职责表达跨 run 来源。

适用：`M3-C01`/`M3-C16`–`M3-C18`、`M3-A01`/`M3-A09`/`M3-A10`、`M6-C10`、`M7-C08`、`M8-C02`/`M8-C04`/`M8-A02`、`M9-C10`。引用边界已确认，具体校验实现和历史来源 DTO 继续定型；尚未修改后端实现。

### D59：Agent 准备执行时创建 session

用户确认水体 Agent 在所有上游推理完成、即将开始自己的推理 loop 时创建独立 session；问题解析 Agent 同样在准备执行解析时创建 session。

- DAG 确定或发现水体时不批量创建全部水体 session。尚未执行的水体由 run 的拓扑及实际调度过程记录表示，此时没有 Agent 会话可读；不能仅因拓扑包含该水体就伪造空会话或推理结果。
- 当水体满足执行条件、准备开始自己的 loop 时创建 session，绑定原 run 与 COMID，并保持 D50 的每水体单次触发。上游失败或数据不足是否允许下游执行仍由 M7 调度语义定型，本项不将“上游已结束”解释成无条件启动。
- 问题解析 session 在准备执行解析时创建，属于原 run，不绑定水体 COMID。原始请求、run 创建记录和 BFS 等公共事实仍直接属于 run，不随 session 创建而转移归属。
- 已创建的 session 即使随后启动失败、执行失败或取消，也保留原身份、自身状态和已有过程。run 在某水体进入执行准备前结束时，不为该水体补造 session；保存重试和历史读取不触发创建或重新执行。

session 的 created_at 表达自身逻辑创建时间，不复用 run 或 DAG 的创建时间；其状态及 updated_at 继续由自身执行流程维护，状态枚举按后续 D60 确认。当前读取与严格历史读取仍遵守各自来源规则，数据库暂未读到 session 不能单独证明内存中从未创建它。

本项确认逻辑创建时机。run 首次创建仍按 D02 确认 PostgreSQL 提交后才启动工作流；执行中 session 的身份、状态及适用记录沿用 run 范围的增量写入、原子提交和补写规则，不额外要求每次调用 Agent 前同步等待数据库提交，也不新增调度状态表。

参考实现是在 Agent 调用准备阶段建立独立会话，本项目借鉴这一创建时机，并按已确认 DAG 依赖和单次 loop 语义使用。前端只有在对应 session 存在时才能读取该 Agent 的完整过程，不将未执行节点展示为空会话；地图的组织和画法仍由前端设计。

适用：`M3-C01`/`M3-C03`/`M3-C18`、`M3-A09`/`M3-A10`、`M4-C06`、`M6-C12`、`M7-C01`、`M9-C10`。创建时机已确认，状态枚举按 D60；创建入口与调度实现继续定型，尚未修改后端行为。

### D60：Agent session 使用五种执行状态

用户确认问题解析与水体 session 使用同一组五种执行状态，并保持 session 终态不可改写；保存进度和警告继续按 run 统一管理。

| 状态 | 含义 |
|---|---|
| pending | session 已创建，正在准备执行；不包括等待上游的阶段，等待节点按 D59 仍属于 run 拓扑与实际过程。 |
| running | 正在执行该 Agent 自己的 loop。 |
| completed | 本次业务执行完成，不表示整个 run 完成或所有记录已保存。 |
| failed | 该 session 的准备或执行失败，已有身份与过程保留。 |
| cancelled | 该 session 的本次执行被取消，已有记录按既定可见性规则保留。 |

执行流程从 pending 开始，进入 running 后可进入 completed、failed 或 cancelled；准备阶段失败或取消可直接由 pending 进入 failed 或 cancelled。终态一旦确定便不再改变，后续保存确认、保存失败、补写或晚到输出均不能将其改成另一终态或重新运行。run 后续取消也不把已经 completed 的 session 改成 cancelled；各 session 状态不能由 run 当前状态统一覆盖。

session 不增加 completed_with_persistence_error，也不建立自己的保存重试状态与预算。D38 的 completed_with_persistence_error 仍属于 run 整体终态；D40 的 persistence 表达该 run 的保存进度和警告。读取 session 的 completed 只能证明所选来源记载其执行完成，不能作为所有过程已保存的证明。

状态及 D55 时间仍由该 session 的执行流程统一生成，存在适用过程记录时按 D25/D53 同事务保存；没有对应公开事件的必要状态更新也必须参与保存确认。枚举不要求增加一套公开生命周期事件，更不要求通过回放 transcript 重建当前状态。开始/结束等实际过程记录、错误表示及取消传递的具体接入随相应执行阶段定型，不复制原结果或错误全文。

参考实现区分创建、执行和各种终态。本项目借鉴这一划分并沿用已有状态命名，按一次独立 loop 与 run 统一持久化职责采用上述五态；不引入其额外恢复状态或单独交付状态。

### D61：重启时分别处理 run 与 session 的遗留状态

用户确认，服务重启后以 PostgreSQL 已保存的状态为依据，分别检查 run 与 Agent session，第一版不自动恢复或重新执行分析。

| 数据库中的遗留记录 | 处理 |
|---|---|
| pending/running 的 run | 标记为 failed，记录 service_interrupted 原因；保留原身份、创建信息和已保存过程。 |
| pending/running 的 session | 标记为 failed，记录 service_interrupted 原因；保留原身份、归属及已保存过程。 |
| 任一层已经保存的终态 | 保持原状态、结果和过程，不因本次重启或另一层状态改变而改写终态。 |

检查 session 时不能仅扫描非终态 run 的子会话。即使所属 run 已 completed、failed 或 cancelled，其下数据库中仍为 pending/running 的 session 也按上述规则处理，避免永久显示执行中；run 的原终态保持不变。completed_with_persistence_error 同样属于 run 已确定的终态。

本项只处理已保存事实。进程丢失前可能存在尚未保存的状态、内容或 session，重启后不能猜测补齐、从旧结果重建执行过程，或为 DAG 的未执行节点补造空会话。这里的 failed/service_interrupted 表达执行被服务中断且不能确认其后续完成，不证明对应 Agent 曾经输出过业务失败结果。

状态修正与其适用的中断记录按 D25/D53 同事务保存，沿用原 run/session 身份及既有正文模型。旧记录、创建时间、原创建回执和原过程序号保持不变；修正的 updated_at 与新中断记录时间表达本次实际处理时间，不伪装为无法确定的进程中断时刻。新记录延续所属 run 的 transcript_sequence。再次启动时已修正为终态的记录不重复修正或追加同义中断记录；具体事务分批、错误表示与提交核实随实现定型。

第一版仍按 D06 使用单 worker。本项不引入跨进程执行接管、会话恢复或工作流重跑；原创建 key 重试继续返回原创建回执，不重新启动分析。重启后没有原 live state 的 run 沿用 D17 的历史读取入口，不伪造活动 SSE 或可恢复的未保存内容。

参考实现会分别核对未结束的子执行，本项目借鉴逐个核对及保留已确定终态的原则，并遵守既有不自动恢复执行的范围。遗留记录处理结果按本项确认，启动顺序和失败行为按后续 D62；具体错误 DTO 与处理实现继续定型。

适用：`M2-C13`、`M3-C03`/`M3-C08`/`M3-C09`/`M3-C14`/`M3-C15`/`M3-C18`、`M3-A04`/`M3-A08`/`M3-A10`、`M9-C07`/`M9-C10`。本项已同步设计和验收契约，尚未实现启动扫描或数据库写入。

用户接受两类流使用不同的恢复语义：在对应 live state 仍保留、允许继续读取实时流时，run SSE 重连直接发送最新完整轻量快照，不逐条补播断线期间的旧状态通知；session SSE 重连按已消费游标补齐未消费的可见过程记录。

例如，断线期间某水体从推理中变为完成，run 重连只需通知当前已完成及同一快照中的其他最新状态。用户查看该 Agent 时，仍可取得断线前后完整的可见过程，不能因为 run 没有补播旧通知就丢失消息、工具调用、证据或结果。run 通知不是完整过程的替代品，也不是所有中间状态变化的历史日志。

run 快照继续按 D69/D71 从原 run、session、BFS/调度及保存事实装配，不为重连保存通知日志或逐份快照。原始记录及适用状态更新仍按既定持久化规则保存，不要求通过回放通知重建状态。session 续传保留事件身份与去重能力，按 D78，run 状态通知不编号，session 使用独立整数消费游标；不能与 run 内 transcript_sequence 或历史列表游标混用。

GET 仍用于首次加载、断线后的状态核对及历史读取。所选 session 的完整过程读取继续按 D45 一次返回完整有序记录，大正文按 D23/D57 读取原全文；取消后的当前可见性限制保持不变，严格历史只返回 PostgreSQL 已保存事实。断线恢复不重新执行分析、不取消分析，也不触发数据库补写预算重置。

本项不改变 D70 的正常关闭条件和 D17/D19 的实时保留边界：重启或 live state 已清理后，已有历史返回 410 并引导历史读取；确认两处均不存在才返回 404，数据库故障明确报错。不能将数据库历史包装成可恢复执行的实时 session。GET/SSE 状态优先级随后按 D74、首次过程读取与订阅衔接按 D75 确认；结束通知随后按 D76 确认为 stream_end，成功握手随后按 D77 确认，消费游标按 D78，具体 payload 仍待定型。

适用：M3-C15/M3-C17、M3-A08/M3-A09、M4-A04、M9-C08/M9-A05。恢复语义已确认，详细协议及实现尚未交付。

### D74：当前状态以 SSE 为准，不引入快照版本号

用户明确不需要 state_revision，GET 与 run SSE 的状态交叠使用来源优先级处理：当前页面实时订阅期间，已经收到的 run SSE 状态优先，迟到的 GET 响应不覆盖它。首次尚未收到 SSE 状态时，GET 可用于初始加载；GET 的断线核对及历史读取职责继续保留，重连后按 D73 接收最新 run 快照。

本项目不为此增加运行期快照计数器、API state_revision 或数据库版本列，也不要求前端比较时间戳判断两路状态的新旧。客户端如何组织请求和状态更新由 M9 按此规则实现，不继续扩展为并发响应的版本协议。

优先级仅用于当前页面的状态展示，不改变后端原状态机、原子保存及来源选择规则。SSE 可见事实不代表已经保存，持久化状态与警告保持 D40 原义；严格历史继续只读 PostgreSQL，不由 SSE 补齐或覆盖。GET 的结果、完整过程及大正文读取能力不因状态优先级被取消。

session SSE 按 D73 保留过程续传游标及去重；typed content/event 的 schema version 和历史列表游标版本也保持原义，它们均不是本项否决的运行期状态快照版本号。首次过程读取与订阅衔接随后按 D75 确认，消费游标按 D78、成功握手按 D77，具体 SSE 事件与错误正文继续定型。

适用：M3-C15/M3-C17、M9-C08/M9-A05。来源优先级已确认，尚未修改后端或前端实现。

### D75：首次订阅 session 流先发送已有过程，再持续推送新增记录

用户接受：打开尚未结束的 Agent 过程时，首次订阅所属 session SSE 不带消费游标；后端先按原顺序发送该 session 已有的全部可见过程记录，再持续发送新增记录。前端无需先 GET transcript 再建立 SSE；两段之间产生的记录也必须接续发送，不能出现遗漏或依赖用户刷新才能补齐。

断线重连按 D73 携带已消费游标，仅补齐尚未消费的可见记录，使用原事件身份去重。首次和续传复用同一记录来源、内容解析及可见性规则，不为首次发送复制一份 transcript 或建立独立历史模型；原 item_id、所属 run/session、transcript_sequence 与引用保持不变，SSE 消费身份和游标按 D78，具体事件 DTO 继续定型。

“全部可见过程”指所选 session 的完整有序记录，不只发送最终总结引用的几条、不按固定条数截断，也不混入其他 Agent 的无关过程。大正文继续使用既定预览和 content_ref，并可按 run_id + item_id 读取原全文；显式公共引用保留原归属，按既定读取能力取得公共上下文，不把公共全文复制到每个 session。取消后晚到内容仍受原可见性限制。

按 D68，已结束 Agent 和历史仍通过统一 GET 读取完整过程及全文；这些接口继续保留，不因实时首次订阅可从头发送而删除。当前 auto 读取与严格 view=history 语义、保存警告、两层流的 D70 结束条件和 D17 的 410 历史边界保持不变。SSE 订阅不创建、执行或取消 Agent，也不因发送已有记录重新触发持久化。

参考实现提供单个会话的完整有序记录装载，本项目已有 M2 单流支持先发送已有事件、再等待新事件。本项借鉴记录装载与接续发送的方式，按新的 run/session 归属扩展到真实 Agent 过程；不将原 M2 整体会话误当作已实现的 Agent session，也不照搬参考实现的会话恢复执行行为。

适用：M3-C15/M3-C16/M3-C17、M3-A08/M3-A09、M9-C08/M9-C10、M9-A05/M9-A07。首次订阅与已有过程的衔接方式已确认，具体事件、游标编码和结束握手尚未实现。

### D76：两类 SSE 用 stream_end 明确通知正常结束

用户接受两类 SSE 使用明确的 stream_end 通知：满足 D70 对应流的正常关闭条件后，后端先发送该流应发送完的内容，再发送 stream_end，随后关闭连接。客户端收到后停止该订阅的重连；未收到就意外断开，按连接中断处理，不能仅凭 EOF 判断 Agent 已完成或分析成功。用户主动关闭视图或离开页面仍按 D68/D69 释放连接，不因此自动重连或取消分析。

session 流在该 Agent 已结束且全部应发送的可见过程发完后通知 stream_end，不等待其他 Agent 或整次 run 的保存；run 流仍须同时满足业务已终态、执行已收敛和全部必需写入已确认，发送最终保存情况后再通知 stream_end。保存为 pending/retry_exhausted 时不能提前结束 run 流，结果交付与 60 秒内存保留门槛保持原义。

stream_end 只表达该流正常结束，不是新的业务终态，不等于分析成功；尤其不能从 session 流结束推断整个 run 已保存完整。业务结果、各层实际终态及保存情况继续读取原状态和内容，run 流的既定保存关闭条件不因这一区分而放宽。

该通知由已有状态及发送完成条件生成，属于连接控制表示，不写入 transcript_items 或其他数据库表，不复制业务结束记录，不增加必需持久化任务，也不更新业务时间或为了通知重新执行分析。四张核心表与原子保存规则不变；按 D78，stream_end 不携带 SSE id、不更新过程游标，具体 payload 继续定型，不能把它当作新的过程正文。

参考实现将内容上报与关闭连接的完成回调分开，本项目借鉴这一分工，增加前端可识别的 stream_end 控制通知。既有业务终态只确定一次、取消后可见性、D73/D75 过程续传与完整读取要求继续保留；重启或 live state 清理后的 410 历史边界不变，已结束时重新握手随后按 D77 统一 200 SSE 和 stream_end，不保留原 204 分支。

适用：M3-C15/M3-C17、M3-A08、M9-C08/M9-A05。结束通知名称和语义已确认，后端与前端实现、完整事件 DTO 和握手响应尚未交付。

### D77：live SSE 统一返回 200，通过 stream_end 结束

用户接受取消旧 M2 的 204 无正文结束分支：M3 两条 SSE 路径在请求合法、身份归属校验通过且对应 live state 仍存在时，统一返回 200 和 text/event-stream，通过 D76 的 stream_end 明确正常结束。参数错误、非法归属或读取故障仍按明确 HTTP 错误处理，不为了统一成功响应隐藏错误。

| 流及状态 | 成功响应中的内容 |
|---|---|
| session 尚未结束 | 按 D75/D73 发送首次已有记录或游标之后的未消费记录，再持续等待和发送新增可见过程；暂时无新记录不表示结束。 |
| session 已结束且仍有未消费记录 | 先补齐全部未消费的可见记录，满足 D70 发送完成条件后发送 stream_end，再关闭。 |
| session 已结束且可见记录已消费完 | 200 SSE 中直接发送 stream_end 后关闭，不返回 204。 |
| run 尚未满足 D70 全部关闭条件 | 发送最新完整轻量快照，再持续通知后续变化；仅业务终态或暂时 up_to_date 不足以结束。 |
| run 已满足 D70 全部关闭条件 | 发送最新完整轻量快照及最终保存情况，再发送 stream_end 后关闭。 |

上述 session 分支覆盖既有实时订阅的恢复，不改变 D68 的正常阅读流程：用户打开已结束 Agent 或历史时仍使用统一 GET，尚未结束时才按需订阅过程。无消费游标时沿 D75 从已有可见过程起点发送，游标与 400/409 校验按 D78，具体错误正文继续定型；不能因握手时发现 Agent 已结束就跳过尚未消费的记录。

重启或 live state 已清理后，存在对应已保存历史则返回 410 并引导 view=history；内存与数据库均确认不存在才返回 404，数据库故障明确报错。原创建与 runtime 注册窗口仍需正确协调，不能误判为历史。成功建流后的传输错误保持中断语义，不在流尾追加 HTTP 错误正文。

本项简化正常结束的传输分支，不改变业务状态、取消可见性、完整过程读取、保存重试、D19 清理门槛或四表职责。stream_end 继续由既有状态生成，不落库、不占用必需写入，也不重跑 Agent。M9 统一客户端按 200 事件流和 stream_end 处理正常结束，不为 M3 目标路径保留旧 204 兼容分支。

参考实现的相关入口采用建立事件流后由完成回调关闭连接的方式，本项目结合 D76 已确认的控制通知统一成功握手。现有 M2 实现仍包含 204，其代码和已实现证据保留为历史基线；在 M3 替换路径时同步修改实现、OpenAPI、raw frame 示例、smoke 与验收，不将本次文档修改视为行为已交付。

适用：M3-C15/M3-A08、M9-C08/M9-A05。成功握手与正常结束分支已确认，事件 DTO、消费游标和错误正文仍待定型，实现尚未交付。

### D78：session 过程使用整数游标，控制通知不编号

用户接受沿用现有 M2 的简单整数游标与校验方式，并按实际 Agent session 划定作用范围：每个 session 的公开过程事件从 1 开始严格递增编号，SSE id 使用该编号的十进制表示。原事件重发保留原编号，不按订阅次数、连接或补写次数重新分配。前端按所属 run/session 保存最后已消费编号，重连通过 Last-Event-ID 原样回传，按同一 session 的事件身份去重。

session 首次订阅省略 Last-Event-ID，按 D75 从已有可见过程起点发送；沿用非负十进制整数校验，0 表示起点，正整数表示最后已消费事件，只补齐更大的序号。格式非法返回 400 / invalid_event_cursor，超过该 session 已产生的末条公开事件序号返回 409 / event_cursor_ahead；不静默跳过记录、改写游标或返回起点。错误通过握手响应表达，具体错误正文随统一 DTO 定型。

只有 session 过程事件分配 SSE id。run 状态通知、stream_end 以及 keepalive 心跳均不分配 SSE id，不更新过程消费游标；run 重连继续按 D73 同步最新快照，不使用过程游标或引入 D74 已否决的快照版本号。接收控制通知不能覆盖最后已消费的过程编号，客户端也不能将某个 session 的游标复用于另一 session 或 run 通知流。

SSE 序号服务于进程内的过程续传，与 item_id、run 内 transcript_sequence 和 query 历史列表游标分工不同。D56 不增加 session 局部 transcript 编号的规则保持不变；session 记录仍保留筛选后的原 run 序号，不把 SSE id 当作持久化记录顺序或据此改写原记录。没有订阅者时产生的可见过程也须保留原事件身份，后续首次订阅能完整读取。

不为 run 通知、stream_end 或心跳增加持久化日志、正文副本或业务状态；原本应保存的过程及状态继续遵守既定原子提交和补写规则。live state 已清理或重启后仍按 D17/D77 转历史，不从 PostgreSQL 重建可续传实时流。合法游标对应的已结束 session 仍按 D77 返回 200 SSE，补齐后发送无 id 的 stream_end，不恢复旧 204 分支。

参考实现已检查的相关入口没有可直接复用的 Last-Event-ID 协议，本项目复用现有 M2 的整数解析、400/409 校验与原事件续传方式，按两层流调整编号范围。M3 两层事件 DTO、过程事件与原记录的具体装配仍需定型，逐段推送与消息级正文存储随后按 D79 确认，具体消息生命周期和 DTO 继续定型。

适用：M3-C15/M3-C17、M3-A08/M3-A09、M4-A04、M9-C08/M9-A05。编号、续传请求头、控制通知不编号及游标错误规则已确认，尚未修改实现。

### D79：实时增量推送，数据库按消息保存一份正文

用户接受提供逐步输出的打字效果，采用“实时增量推送、数据库按消息保存一份正文”。此前“消息生成结束后才推送、首版不提供逐 token 效果”的建议未获接受，不作为实现限制。

模型生成过程中，所属 session SSE 持续推送文本小片段，前端根据稳定消息身份更新同一条消息。生成结束后整理该消息实际得到的正文，纳入既有 transcript 保存；片段与最终消息保持关联，不能将一次消息展示为片段拼接与完整正文两条重复消息。消息身份按 D81 在开始生成时分配 item_id，片段与最终正文复用；具体事件字段及未完成消息的 DTO 继续定型，不为流式显示新增消息表或同义执行身份。

PostgreSQL 按消息保存组装后的正文，不把每个 token 或实时片段另存为 transcript item，也不同时保存一套片段全文与一套同义聚合全文。正文按 D23 在内联与独立大内容之间选择一处保存，保留原版本、归属及显式引用。工具调用、证据、hook、错误等各自的真实过程事实继续保存，不因文本按消息聚合而压缩为最终总结或取消完整过程读取。

在 live state 保留期间，文本片段属于 session 过程流，按 D78 分配稳定的整数 SSE id，首次订阅与重连按 D75/D73 补齐可见过程；不因消息已经整理完成而随意删除仍需续传的片段或重新编号。历史读取只返回 PostgreSQL 已保存的消息及其他过程事实，不需要重演原来每个字出现的节奏，不从内存补入未保存片段。SSE 编号与 transcript_sequence 继续分开，不要求每个 SSE 事件对应一条数据库记录。

失败或取消时，保留实际已产生的内容并明确未完成语义，不能丢弃已知内容或假装生成成功。取消后的晚到内容仍遵守 D10/D67 的审计与当前可见性限制，不能借拼接消息把晚到结果重新送给前端或下游。D80 已确认生成中正文计入保存状态及结束或中断后再写入；取消前正文与晚到审计的组织按 D84；具体未完成正文整理及当前读取 DTO 继续定型；已确认内容、补写、原子提交与清理保证保持不变。

片段进入 SSE 和可读取内存前必须按 D27 处理凭据，并支持跨片段识别。不能先把拆开的凭据推送出去，再等完整正文生成或落库时补做脱敏。持久化边界仍执行同一规则，全文、预览和字节数基于安全正文；具体缓冲及脱敏实现继续定型。D23 阈值控制正文存储与全文装载，不将已确认的实时逐步输出变成只显示最终预览，也不改变前端按语义折叠 tool/skill/hook 的规则。

参考实现分别处理文本片段回调和生成结束后的完整消息，本项目借鉴这一区分。run SSE 仍只负责轻量状态与保存通知，片段留在所属 session 流；控制通知不落库，四张核心表和单一事实原则不变。M3 提供通用能力与测试记录，真实模型输出按 D28 由后续问题解析、水体 Agent 等实际生产阶段接入，M9 实现逐步显示与去重。

适用：M3-C02/M3-C05/M3-C06/M3-C15/M3-C16/M3-C17、M3-A03/M3-A07/M3-A08/M3-A09/M3-A10、M4-C07、M6-C10、M9-C08/M9-C10、M9-A05/M9-A07。流式显示与消息级单份正文方向已确认，保存状态配合随后按 D80 确认；具体消息生命周期及 DTO 尚未实现。

### D80：未定稿正文计入 pending，整理后再触发写入

已产生且属于必需保存内容的消息正文，在生成中尚未整理定稿时也计入 run 级 persistence.pending，不能因为写入队列暂时为空便返回 up_to_date。没有实际保存错误时 warning=null，正常生成与等待不伪造持久化失败。GET 与 run SSE 从相同的 live 消息、待写内容、提交确认和重试预算计算，不新增数据库状态字段或第二份正文队列。

消息结束或中断后，整理实际已产生的正文，再交给原串行写入器按既有规则保存；失败或取消保留未完成语义及原可见性限制。仅因正文还在生成不执行数据库写入，不保存周期性的半成品全文，不消耗数据库重试次数。其他已可写的记录和状态继续按 D25/D37 正常保存，不必等待这条消息结束；适用的原子记录组仍不可拆开。

已有补写耗尽时，保留 retry_exhausted 和原保存错误，新片段不将状态降为普通 pending，也不重置预算或重新唤起写入器。生成结束后的实际写入仍沿用每轮最多 5 次重试、退避、原批次优先和手动恢复规则；不能以消息定稿为由另开一轮。当前必需正文与状态均实际确认保存后才可返回 up_to_date，run 通知流结束和 live 清理继续检查各自的全部条件。

D41 的 HTTP 行为不变：pending 请求返回 202，继续由原写入器负责。若仅在等待消息定稿，收到请求不会强制结束生成、提前保存部分正文、执行空事务、另建写入器或启动重试；必须确有原写入器负责后续处理。前端将 pending 理解为尚未全部保存，不能从 pending 或 202 推断数据库正在执行 SQL，手动入口仍仅在 retry_exhausted 提供。

借鉴参考实现区分文本增量回调与完整消息整理的做法，本项目的保存状态、原子提交和补写预算按上述规则统一维护。严格历史仍只读 PostgreSQL 已保存的事实，生成中的内容不会因状态显示 pending 而进入历史；没有订阅者也不改变保存责任。

适用：M3-C12/M3-C17/M3-C18/M3-C20、M3-A06/M3-A07/M3-A12、M9-C11/M9-A08。保存状态和写入触发边界已确认，消息身份随后按 D81 复用 item_id；具体消息 DTO、未完成内容整理和取消边界组织继续定型，尚未修改实现。

### D81：流式片段与最终消息复用 item_id

一条流式消息开始生成时，由后端分配一次全局唯一 UUID 作为 item_id；该消息的所有文本片段和最终整理的正文都携带并复用这个身份。生成结束、未完成内容整理、保存补写、重新读取与全文展开均不另换 ID，不按内容文本计算或合并独立消息。原 run_id、session_id 归属及引用校验继续适用。

D84 对取消后的新增片段明确边界：它们属于引用原消息的独立审计事实，不再追加到已经固定为 incomplete 的原消息，也不借原 item_id 改写可见正文。

前端按 item_id 将片段追加到对应消息，最终正文更新同一条消息，不能再插入一条重复消息。片段重发的去重仍使用 D78 的 session SSE 整数 id；同一 item_id 会合法对应多个不同片段，不能仅凭 item_id 丢弃后续片段。SSE id 表示一次过程推送，item_id 表示原消息，transcript_sequence 仍表达 run 内记录顺序，三者不互相替换。

提前分配 item_id 只确定身份，不因此提前写入数据库占位记录或部分正文。消息结束或中断后按 D79/D80 整理实际内容并交给原写入器，正文仍只在内联或独立大内容中保存一份。已有的 live 保存状态、有限重试、取消后可见性、原子提交与严格历史读取规则保持不变；拥有 item_id 不代表已经保存。

参考实现将片段关联到已有消息身份，本项目借鉴这一方式并直接使用 transcript 的 item_id，不新增同义 message_id、消息表或身份映射表。session_id 继续表示一次 Agent 完整 loop，operation_id 继续表示一次模型或工具调用，不能用它们代替多条消息各自的身份。

本项确认消息身份的分配与复用；流式消息进入 D56 统一序列的时机及 D55 原创建时间随后按 D82 确认，均在开始生成时确定并先保留在内存，不因分配这些信息而提前落库或完成正文定稿。

适用：M3-C01/M3-C15/M3-C16/M3-C17、M3-A01/M3-A08/M3-A09/M3-A10、M9-C08/M9-A05。M3 验证通用消息能力，真实模型输出仍由后续实际 Agent 阶段接入；尚未修改实现。

### D82：消息开始时固定过程序号和创建时间

一条流式消息开始生成时进入统一记录入口，同时确定 D81 的 item_id、D56 的 run 内 transcript_sequence 和 D55 的 created_at。过程序号固定该消息在完整过程中的位置，创建时间表达开始生成时刻，API occurred_at 从同一值装配；生成结束、整理未完成内容、保存及补写均保留原值，不增加第二套顺序或通用时间字段。

上述信息先保留在内存，消息在同一位置持续接收片段，结束或中断后再整理正文交给原写入器。正文定稿不会将原消息移到过程末尾，也不会重新分配 transcript_sequence、刷新 created_at 或插入第二条同义消息；数据库仍保存一份最终整理正文，不提前写占位行或半成品全文。

其他已可写记录和状态继续按 D25/D37/D80 正常保存，适用原子组及引用约束不拆开。较大序号的记录可以先于仍在生成的较小序号消息保存；实际提交只确认该批真实内容，不能用数据库中最大的 transcript_sequence 将之前所有序号一并确认。D38 的固定范围判定、D40 的保存状态、D70 的 run 流结束和 D19 的清理门槛均保留逐项实际保存要求，具体批次和待确认集合的表示随实现定型。

当前与历史的完整过程仍按原 transcript_sequence 排列，SSE id 仍独立表示发送事件及续传顺序，不按消息定稿或数据库提交顺序重排。严格历史只显示已保存记录；较早消息尚未保存时不补造占位内容，也不从 live state 补齐。后来保存的消息按原序号出现在相应位置，不能仅凭序号间隙或较大的已保存序号推断完整性。

参考实现先建立消息及顺序关系，再填充正文，本项目借鉴这一组织方式；时间按本项目已确认的开始生成语义固定。消息生成状态随后按 D83 确认，取消边界前后内容组织按 D84，具体未完成正文 DTO 及跨片段脱敏继续定型，不改变既有取消、补写和单一事实要求。

适用：GLOBAL-C10、M3-C01/M3-C02/M3-C04/M3-C17/M3-C18、M3-A02/M3-A07/M3-A09/M3-A10、M9-C08/M9-C10/M9-A05/M9-A07。消息入序和原创建时间已确认，尚未修改实现。

### D83：消息正文使用三种 generation_status

用户确认在消息正文中使用 generation_status 描述这条消息的生成情况，三个值如下。该字段属于适用的消息内容类型，不给请求、工具证据、生命周期事件等所有 transcript 类型强制增加同义公共状态。

| generation_status | 含义与保存范围 |
|---|---|
| generating | 这条消息正在生成，正文可以持续增加；只存在于 live state，不作为数据库正文状态保存。 |
| completed | 这条消息正常生成结束；整理后的正文以此状态按原规则保存。 |
| incomplete | 因取消、错误或输出截断而未完整生成；保留实际已产生内容，整理后的正文以此状态按原规则保存。 |

生成中消息按实际结果整理为 completed 或 incomplete，继续复用 D81/D82 已确定的 item_id、transcript_sequence 和 created_at，不因状态改变另造消息或刷新创建时间。正文整理完成后按既有不可变记录规则保存和补写，不能在保存重试时重新判断或改写当时的生成结果。具体中断原因、模型结束原因及错误关联的 DTO 随消息内容类型定型，已有真实错误和过程记录仍须保留。

generation_status 只描述一条消息。消息 completed 不表示整个 Agent loop 已结束、run 已成功或正文已经保存；Agent 后续工具失败、run 后续取消或数据库保存失败，不反向修改已经正常生成完的消息。消息 incomplete 也不能单独代替 run/session 的执行终态或 persistence 保存信息。SSE 断线及 stream_end 不作为消息生成成功的依据。

该字段在消息正文中维护一份，API 复用相同消息模型与解析，数据库不增加同义 generation_status 查询列或另一份公共元信息。generating 仅用于 live 读取与推送；严格历史只返回 PostgreSQL 实际保存的 completed/incomplete 正文，不从内存拼入生成状态或伪造生成中占位记录。D79 的单份正文、D80 的 pending 与重试预算、D82 的实际提交确认规则保持不变。

参考实现区分消息的生成、结束、取消及错误，并保留模型结束原因。本项目借鉴其区分消息与执行过程的做法，按上述三态收敛生成状态；取消边界前后内容组织按 D84，具体当前读取 DTO 和跨片段脱敏继续定型。M3 用测试消息验证通用能力，真实模型消息类型仍由 D28 对应实际 Agent 阶段扩展。

适用：M3-C02/M3-C10/M3-C17/M3-C18、M3-A05/M3-A07/M3-A08/M3-A10、M4-C07、M6-C10、M9-C08/M9-A05。三态及正文单一来源已确认，尚未修改实现。

### D84：取消时固定原消息，晚到正文另存审计

后端按 D67 接受 run cancel 时，将仍在生成的消息固定在当时已接收的内容，generation_status 变为 incomplete，继续保留 D81/D82 原 item_id、transcript_sequence 和 created_at。边界以服务端接受取消为准，不等数据库提交、客户端收到响应或在途调用实际返回后再确定；与片段接收共用统一取消检查和同步边界，具体锁组织随实现定型。已经正常生成完的 completed 消息及各层既定执行终态不改写。

取消后到达的片段不再拼接到原消息，合并为独立的审计记录，显式引用原消息，只保存新增内容，不重复保存原消息前缀或另造一份前后拼接的全文。审计继续属于原 run/session，适用 operation_id 沿用原调用；作为独立事实使用自己的 item 身份、原顺序和实际产生时间，不覆盖原消息。仍使用 transcript_items 与适用的 transcript_contents，不增加审计表或 produced_after_cancel 一类冗余布尔字段；具体审计内容类型、字段、片段整理及调用最终响应的衔接随 DTO 定型。

当前 GET 和 session SSE 仅保留原消息在取消边界固定的正文，晚到审计不得进入当前展示或下游。该规则贯穿列表、原消息全文、审计全文及显式引用读取；auto 回退 PostgreSQL 后也不放宽。严格历史仍只读已保存事实，可读取原消息与其晚到审计，按显式关联追溯完整内容，不能通过拼接或刷新原消息将晚到内容恢复为当前可见正文。

固定的原消息和晚到审计分别按既有正文阈值、凭据脱敏、原子提交和补写规则保存。审计引用的原消息须已保存或与其同批保存，不能写出缺失目标；补写保留各自原身份和正文，不因分开保存而重复全文、放弃完整过程或重置重试预算。晚到审计中的已产生但尚未保存内容仍计入必需保存范围；run 流结束和 live 清理继续等待执行收敛及全部适用内容实际保存。

取消只固定内容边界，不绕过 D27/D79 的安全处理。待处理片段与跨片段凭据仍需按同一脱敏规则处理后才能进入可读取正文，不能借取消定稿提前输出未经处理的内容；具体缓冲及跨边界处理继续定型。原消息的 incomplete 通知按 D85 使用 message_finalized，不能将晚到正文混入该通知；具体事件 DTO 随统一协议定型。

参考实现的取消标记及保留既定终态可以借鉴；本项目按已有当前可见性与历史审计要求明确上述正文拆分。M3 验证通用存储和读取，实际 Agent 阶段接入真实取消与在途输出，M9 遵守展示和来源边界。

适用：M3-C05/M3-C06/M3-C10/M3-C12/M3-C16/M3-C17/M3-C18、M3-A03/M3-A05/M3-A07/M3-A08/M3-A09/M3-A10、M7-C04/M7-A04、M9-C08/M9-A05。取消正文边界与独立审计方向已确认，定稿事件随后按 D85 确认；具体 DTO 与安全处理尚未实现。

### D85：消息定稿时发送 message_finalized

一条可见消息正常生成结束或中断并完成正文整理时，在所属 session SSE 中产生一次 message_finalized 事件。事件携带该原消息的定稿表示，包括原 item_id 及同源于正文的 generation_status=completed/incomplete，复用 D81/D82 的原身份、顺序、时间和归属；不等数据库保存成功，也不因补写成功再产生一次同义定稿事件。

正文继续按 D23 的现有装载规则表示：小正文内联，大正文提供预览和原全文引用；从原消息和同一解析/装载实现组织事件，不由调用方分别填写另一套状态或正文。预览不代表完整消息，前端不能把预览作为完整正文追加或覆盖已经展示的正文；全文仍通过同一 run/item 入口按当前来源与可见性读取。具体事件 envelope、字段层级及正文校准方式随完整 DTO 和前端实现落实。

message_finalized 从原消息定稿事实生成，不额外追加一条同义 transcript item，不保存第二份正文，也不让这个传输事件再触发必需写入。它属于 session 过程事件，按 D78 分配一个稳定的整数 SSE id；没有订阅者时也保留该事件，首次订阅和断线续传按原规则发送。重发使用原 SSE id，前端去重并更新原消息，不能把重发理解为重新生成、再次定稿或创建第二条消息。

按 D84 取消时，事件只包含在取消边界固定的原正文及 incomplete 状态，不包含晚到审计，不把已经 completed 的消息重新改为 incomplete。取消、错误和截断后的未完成语义均按 D83 保留，事件不能将中断包装为正常生成成功。凭据处理和晚到可见性继续适用于该事件、预览和全文引用。

该 session 应发送的 message_finalized 必须先于其 stream_end。前端据此结束这条消息的打字状态；Agent 可以继续产生其他消息，不因一条消息定稿而关闭整个 session 流、判断 run 已结束或宣称内容已经保存。stream_end 仍按 D70/D76 表达该流正常结束且不分配 SSE id，保存进度继续按 D40 从原事实生成。

参考实现除增量外还发送结束信息及最终文本，本项目借鉴明确结束通知的做法，以消息定稿为本事件的边界。模型调用结束、消息定稿、Agent 结束和保存确认保留各自含义，不照搬参考实现的身份层级或额外存储。M3 验证通用事件、装载和续传能力，真实消息由后续实际 Agent 阶段接入，M9 实现展示。

适用：M3-C05/M3-C10/M3-C15/M3-C17/M3-C18、M3-A03/M3-A05/M3-A07/M3-A08/M3-A10、M9-C08/M9-A05。事件名称、生成时机、原记录复用和流结束顺序已确认，具体 DTO 与实现尚未交付。

### D86：消息流划分为开始、增量和定稿事件

用户接受按消息划分三个 session SSE 事件，补齐 D85 已确认的定稿事件：

| 事件 | 职责 |
|---|---|
| message_started | 从开始生成的原消息取得身份、run 内顺序、原创建时间、内容类型/版本及必要归属，表明开始生成。 |
| message_delta | 携带 item_id 与本次新增文本；在保留统一事件所需关联和版本信息的前提下，不反复携带完整消息元信息或累计全文。 |
| message_finalized | 按 D85 携带原消息定稿表示，generation_status 为 completed/incomplete，结束这条消息的打字状态。 |

对同一消息，开始事件先于其任何增量，定稿事件在其可见增量之后；不同消息或其他真实过程可以按发生顺序交错，通过原 item_id 区分。三者都使用该 session 的统一整数 SSE 编号，重发保留原号，首次订阅和续传复用同一事件来源；不新增消息局部续传计数器。run 通知、stream_end 和心跳仍按 D78 不编号。

事件从原消息生命周期与安全文本增量生成，不把每帧变为数据库行，不额外保存累计正文副本。消息开始时先保留 D81/D82 元信息，正文结束或中断后按 D79/D80 整理保存；其他工具、证据、hook、错误等独立事实正常记录。取消后原消息依 D84 固定并按 D85 定稿，晚到正文不再产生该可见消息的 delta；独立审计仍保留且不进入当前过程流。

参考实现分别处理开始、文本片段和结束，本项目借鉴这一分工，按自身消息身份和存储规则组织。字段层级、装配函数及验证规则由实现者直接定型，同步共享 DTO、OpenAPI、SSE 文档与测试；不为这些细节继续拆分用户确认。消息显示、数据库保存和 Agent 执行仍分别遵守原契约。

适用：M3-C02/M3-C06/M3-C15/M3-C17/M3-C18、M3-A03/M3-A05/M3-A08/M3-A10、M9-C08/M9-A05。三类事件及职责已确认，尚未修改运行时代码。

设计以本项目的领域模型、状态机和跨 Milestone 契约为准。实现时保留以下边界：

| 范围 | 实现原则 |

| 存储职责 | D53 四张核心表分别保存 run 当前信息、session 当前信息、原记录及独立大正文，保留 D33 单一事实与全文去重原则。 |
| 会话创建 | D59：问题解析与水体 Agent 均在准备执行时创建 session；水体先等待所有上游完成。此前节点由 run 拓扑与实际过程表示，已创建会话失败或取消仍保留。 |
| 记录时间 | D54/D55：所有业务表每条记录保留时间；M3 可变记录存 created_at/updated_at，不可变记录仅存 created_at，API occurred_at 从同一原值装配，补写不刷新。 |
| 记录顺序 | D56：run 内统一分配 transcript_sequence，所有 session 保留筛选后的原序号；SSE 编号独立，Agent 过程不分页。 |
| 写入确认 | 统一追加入口；旧整体 session 的串行写入与重试预算归到 run，实际提交成功才确认对应批次，失败保留待写内容。 |
| 状态与原子性 | session 按 D60 使用 pending/running/completed/failed/cancelled，终态不改写；run 与各 session 分别维护状态及 D55 时间，适用状态与记录同事务保存。保存进度和警告按 run 管理。 |
| 取消传递 | D67：前端只调用 run cancel；后端先阻止后续调度，再调用内部取消能力覆盖所有已创建的未终态 session。首版不公开单独 Agent cancel HTTP 接口，终态及持久化保证保持原义。 |
| 实时观察 | D69：当前 run 页面连接轻量 run 通知流，按 D68 打开水体实时过程时再连接其 session 流。GET 用于加载、断线核对和历史，打开前的已有过程必须完整可读；通知复用原事实，执行和保存不依赖订阅。 |
| 状态快照 | D71：run 通知采用完整轻量快照，覆盖 run、实际 session、保存状态及 BFS 范围内水体的参与/执行情况。五种水体状态由原拓扑、调度和 session 事实装配，未执行水体不预建 session；取消后展示按 D72 留到 M9。 |
| 流结束 | D70：session 结束并发送完可见过程后关闭其流；run 已终态、执行已收敛且必需内容全部保存后关闭通知流，保存中或耗尽时继续通知，不等待 60 秒 grace，也不延迟既定结果交付。 |
| 断线恢复 | D73：live state 保留时，run 重连发送最新完整轻量快照，不补播旧状态通知；session 按游标补齐可见过程。完整过程读取和严格历史语义保留，不增加通知日志存储。 |
| 状态来源优先级 | D74：当前实时状态以 run SSE 为准，迟到的 GET 不覆盖已收到的 SSE 状态；保留 GET 加载、断线核对与历史读取，不增加 state_revision 或快照版本协议。 |
| 首次过程订阅 | D75：未结束 Agent 的 session SSE 首次无游标，先发送已有全部可见过程，再持续推送新增记录，无需先 GET transcript。重连按原游标补齐，已结束 Agent 和历史仍用完整 GET，大正文和公共引用保持原读取方式。 |
| 结束通知 | D76：两流分别满足 D70 条件后发送 stream_end 再关闭，客户端据此停止重连。该通知不表示分析成功，不是新的业务终态或数据库记录；意外 EOF 不代替明确结束。 |
| 成功握手 | D77：合法请求且对应 live state 保留时，两流统一返回 200 SSE，正常结束用 stream_end；session 先补齐记录，run 先发送最新快照。不保留旧 204 分支，清理后的 410 历史边界不变。 |
| 过程游标 | D78：session 过程事件从 1 递增作为 SSE id，Last-Event-ID 续传且重发保留原号；非法格式 400、超过末尾 409。run 通知、stream_end 和心跳不编号，不改变过程游标或 transcript_sequence。 |
| 流式正文 | D79：session SSE 实时推送文本片段，前端更新同一消息；数据库保存组装后的正文一份，失败/取消保留实际内容和未完成语义。片段可按 live 游标续传，历史读取消息正文，推送前须处理跨片段凭据。 |
| 生成中的保存状态 | D80：已产生但未定稿的必需正文计入 pending，无实际错误则 warning=null；消息结束或中断后整理写入，等待生成不消耗重试。已有耗尽及错误优先保留，其他可写内容照常保存，不新增状态列。 |
| 流式消息身份 | D81：开始生成时分配一次 item_id，片段与最终正文复用，前端更新同一消息；重发片段按 SSE id 去重，分配消息身份不触发数据库占位或正文写入。 |
| 流式消息顺序与时间 | D82：开始生成时统一确定 item_id、transcript_sequence、created_at，occurred_at 同源；先留在内存，定稿和补写不移动位置或刷新时间。其他可写记录照常保存，较大已保存序号不能代替全部保存确认。 |
| 消息生成状态 | D83：消息正文使用 generating/completed/incomplete；generating 仅存在 live，整理后按 completed/incomplete 保存，不新增同义数据库列。消息生成状态不替代 Agent/run 终态或 persistence。 |
| 取消中的正文 | D84：服务端接受 run cancel 时固定生成中原消息并标 incomplete，保留原身份、顺序和时间；晚到片段合并为引用原消息的独立审计，仅保存新增正文。当前 GET/SSE/下游不读取晚到审计，严格历史可读已保存关联。 |
| 消息定稿事件 | D85：正常结束或中断后产生一次 message_finalized，携带原消息定稿表示且不等保存；正文按原内联/预览引用规则装载，事件按原 SSE id 续传，不另存同义记录，先于 session stream_end。 |
| 消息流阶段 | D86：message_started 提供原元信息，message_delta 只传原消息的新增文本，message_finalized 完成定稿；共用 session SSE 编号，不逐帧入库或重复发送累计全文。 |
| 重启遗留 | D61：分别将已保存的非终态 run/session 标记为 failed/service_interrupted，已终态 run 下的遗留 session 也检查；各层原终态不变，不恢复执行或补造未保存内容。 |
| 应用启动 | D62：连接检查、schema 检查、遗留处理依次成功后才接收请求，任一步失败退出并给出安全修复提示。D63：结构版本由 Alembic 统一管理且必须与当前代码要求完全匹配，初始化/升级使用独立命令。 |
| 内容与引用 | D57 全文引用使用 run_id + item_id；D58 普通过程引用限于同 run、允许跨 session，跨 run 证据使用明确历史来源。完整读取所选水体 session 的过程及显式公共引用，原正文保持一份。 |
| 凭据脱敏 | 进入可读取内存与持久化边界使用同一脱敏规则；日志保留普通 query，全文、预览和字节数基于安全正文。 |
| 幂等创建 | run 的数据库唯一 key、原请求体指纹与原创建回执保持一致；同 key 重试不重新分析，未确认提交不能提前启动。 |
| 查询方式 | 目标路径按 D65。当前读取自动选择来源，历史只读已保存事实；run 列表按 D47–D50 分页。D64 在 run 详情返回原会话简要信息，以 run_id + session_id 定位水体结果和 D45 完整过程，不另建 COMID 映射或第二套入口。 |
| 清理与配置 | live state 清理遵守终态、quiesced、全部保存确认及 grace 条件；PostgreSQL 配置、初始化和升级支持跨环境搭建。 |

[WHATWG EventSource 接口与处理模型](https://html.spec.whatwg.org/multipage/server-sent-events.html#the-eventsource-interface)未向脚本暴露握手响应的 HTTP status/body；普通 error 回调不能直接读取 `410` 的历史入口。[Fetch 文档](https://developer.mozilla.org/en-US/docs/Web/API/Fetch_API/Using_Fetch)说明客户端可以读取 response status 并流式消费 body。D18 已确认采用基于 fetch 的统一 SSE 客户端，由 M9 实现；具体解析库尚未选择。
